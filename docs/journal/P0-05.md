## Why / design decisions (and alternatives rejected)
- **Parallel backend & frontend jobs**: Running backend and frontend in separate parallel runners reduces total workflow duration to ~34 seconds and provides instant feedback on which layer failed.
- **PostgreSQL service container in CI**: Ensures Django models, migrations, and test assertions run against the real PostgreSQL 16 engine rather than SQLite, ensuring parity with local dev and production requirements.
- **Handling private repo branch protection**: Documented the GitHub platform constraint transparently. Rather than making the repository prematurely public during the semester, the team enforces mandatory peer code review and CI verification protocols before every merge.

## How it works (follow ONE request/click end to end)
- When a developer opens or updates a Pull Request targeting `main`, GitHub Actions automatically initiates `.github/workflows/ci.yml`.
- Job 1 (`backend`): Spins up an Ubuntu runner with a PostgreSQL 16 service container, checks out the repo, sets up Python 3.12, installs dependencies via `pip install -r requirements.txt`, runs `python manage.py check`, checks for ungenerated migrations with `python manage.py makemigrations --check --dry-run`, and runs `python manage.py test`.
- Job 2 (`frontend`): Spins up an Ubuntu runner, checks out the repo, sets up Node.js 20, installs dependencies cleanly with `npm ci`, checks code quality via `npm run lint`, and verifies bundle production with `npm run build`.
- Both jobs report status back to the pull request UI.

## How to test (commands / clicks)
- Run backend verification locally: `cd backend && python manage.py check && python manage.py test`
- Run frontend verification locally: `cd frontend && npm run lint && npm run build`
- Run board script on Windows without flags: `python scripts/board.py --me` (verifies UTF-8 icons render cleanly)
- Inspect GitHub Actions workflow status: `gh run list --workflow=CI` and `gh run view <run-id>`

## Gotchas / things that surprised us
- GitHub Free accounts cannot enable Branch Protection Rules or Repository Rulesets on Private repositories via API or UI without upgrading to GitHub Pro (e.g. via GitHub Student Developer Pack) or changing the repository visibility to Public.
- Windows PowerShell defaults standard output encoding to `cp1252` (charmap), causing Python to throw `UnicodeEncodeError` when printing unicode checkmarks (`✔`); setting UTF-8 on `sys.stdout` resolves this cleanly.

   ج: دیتابیس قطعی پروژه PostgreSQL است. تفاوت‌های کلیدی بین SQLite و PostgreSQL در نحوه اجرای مایگریشن‌ها، نوع فیلدها و رفتار تراکنش‌ها وجود دارد. اجرای تست‌ها روی Postgres در CI تضمین می‌کند کدی که در CI سبز می‌شود دقیقاً در محیط واقعی نیز بدون خطای ناسازگاری دیتابیس کار خواهد کرد.
3. س: تفاوت `npm ci` با `npm install` در محیط CI چیست؟
   ج: دستور `npm ci` به طور دقیق و صرفاً بر اساس فایل قفل `package-lock.json` پکیج‌ها را نصب می‌کند، فایل لاک را تغییر نمی‌دهد و دایرکتوری `node_modules` را پیش از نصب پاکسازی می‌کند. این موضوع تضمین می‌کند که بیلد CI کاملاً ایزوله، قطعی (Deterministic) و منطبق با محیط توسعه‌دهنده باشد.
4. س: دستور `python manage.py makemigrations --check --dry-run` چه چیزی را در CI بررسی می‌کند و چرا ضروری است؟

5. س: در اکانت‌های گیت‌هاب رایگان، اعمال وضعیت اجباری برنچ (Branch Protection) روی مخزن Private چگونه است و چه راهکاری برای آن وجود دارد؟

# P3-08 — Logging infrastructure
- Author: A (Amirmohammad Soleimani)   · Reviewer: B (Mahdi Moradi)   · PR: #38   · Date: 2026-11-07

## What was done (3–6 bullets)
- Implemented `RequestLogMiddleware` in `backend/apps/core/middleware.py` which intercepts all incoming HTTP requests and outgoing responses, measuring round-trip duration in milliseconds and logging `method`, `path`, `status_code`, `user_id` (or `'anon'`), and `duration_ms`.
- Added central Django `LOGGING` configuration in `backend/config/settings.py` supporting `console` output alongside three rotating log files (`logs/app.log`, `logs/error.log`, `logs/security.log`) with automatic size rotation (5MB, 5 backups) and UTF-8 encoding.
- Configured configurable log level via environment variable `LOG_LEVEL` (defaulting to `INFO`), and standardized formatters (`standard` with time, level, module name, and message; `verbose` including source file path and line number for error tracking).
- Ensured automatic directory creation for `backend/logs/` at application startup while verifying `backend/logs/` is ignored by Git in `.gitignore`.
- Created comprehensive test suite in `backend/apps/core/tests.py` covering middleware anonymous logging, authenticated user logging, unhandled exception 500 logging, logging dictionary verification, log file rotation, and end-to-end client request logging.

## Why / design decisions (and alternatives rejected)
- **Top of MIDDLEWARE Stack for RequestLogMiddleware**: Placed `RequestLogMiddleware` as the outermost middleware in `settings.MIDDLEWARE`. When a request enters, the middleware starts a high-resolution monotonic timer (`time.monotonic()`), passes control downstream through `SecurityMiddleware`, `SessionMiddleware`, and `AuthenticationMiddleware` to the view, and then in the `finally` block captures the final HTTP status code, user ID from `request.user`, and total duration. This ensures accurate end-to-end latency measurements without premature termination if a view raises an exception.
- **Segregated Rotating Log Files**: Instead of a monolithic log file that combines routine access logs with critical failures, we separated logs into:
  - `app.log`: general application-wide events at `LOG_LEVEL` and above.
  - `error.log`: server errors and exceptions (`ERROR` and `CRITICAL`) using verbose format (with file and line number).
  - `security.log`: security-sensitive events (`django.security`, `security`, `apps.security`) for auditing authentication, authorization, and permission rejections.
- **No Sensitive Data / Password Logging**: In compliance with course security rules (`AGENTS.md`), request payloads, query string passwords, authentication tokens, and session keys are never written to log outputs; only safe metadata (`method`, `path`, `status`, `user_id`, `duration_ms`) is recorded.
- **RotatingFileHandler Over TimedRotatingFileHandler**: Chosen to prevent unbounded disk exhaustion on developer machines and evaluation servers regardless of how long the server runs or how many requests are processed.

## How it works (follow ONE request/click end to end)
1. A client sends an HTTP request, e.g. `POST /api/auth/login/`.
2. `RequestLogMiddleware.__call__` intercepts the request, records `start_time = time.monotonic()`.
3. The request flows through downstream middlewares (`SessionMiddleware`, `AuthenticationMiddleware`) and reaches `LoginView`.
4. The view validates credentials and authenticates the user, setting `request.user = user`.
5. The view returns an HTTP 200 response with JSON envelope `{"data": {"user": {...}}}`.
6. The response bubbles up through the middleware chain back to `RequestLogMiddleware`.
7. In the `finally` block, `duration_ms` is computed, `user_id` is extracted from `request.user.id`, and `logger.info(...)` writes the log line:
   `2026-11-07 23:30:00 [INFO] [apps.core.middleware] POST /api/auth/login/ 200 user_id=2 duration_ms=45.20`.
8. The log record is formatted by `standard` formatter and written simultaneously to the terminal console and appended to `backend/logs/app.log`.

## Gotchas / things that surprised us
- In Django 5.x, `request.user` is populated as a `SimpleLazyObject` by `AuthenticationMiddleware`. By placing `RequestLogMiddleware` at the outer layer and reading `request.user` after `self.get_response(request)` returns, we can safely access `request.user.id` or `request.user.is_authenticated` without forcing premature user evaluation before session lookup has executed.
- When an unhandled exception occurs inside a view, wrapping `self.get_response(request)` in a `try ... finally` block ensures that the request duration and status code (500) are still logged even if the exception bubbles up through custom exception handlers.

3. س: چرا `RequestLogMiddleware` در بالاترین لایه لیست `MIDDLEWARE` قرار گرفته است و چگونه به شناسه کاربر دسترسی دارد؟
   ج: در معماری پیازی میدلورهای جنگو، میدلوری که در بالاترین لایه قرار دارد، قبل از اجرای سایر میدلورها زمان شروع را ثبت می‌کند. سپس کنترل را به میدلورهای پایینی (`SessionMiddleware` و `AuthenticationMiddleware`) واگذار می‌کند. پس از اجرای ویو و هنگام بازگشت پاسخ به سمت کلاینت، میدلورهای میانی کاربر را احراز هویت کرده و شیء `request.user` مقداردهی شده است؛ در نتیجه `RequestLogMiddleware` می‌تواند زمان کل اجرای تمام لایه‌ها را دقیق محاسبه کند و هم‌زمان به شناسه کاربر و کد وضعیت خروجی دسترسی داشته باشد.
4. س: پیکربندی متغیر محیطی `LOG_LEVEL` چگونه کار می‌کند و چه تاثیری در محیط‌های مختلف (توسعه و استقرار) دارد؟

   ج: فایل‌های لاگ داده‌های زمان اجرای سرور هستند که مدام در حال تغییرند و همچنین ممکن است شامل اطلاعات کاربری یا عملیاتی باشند. قرار دادن این پوشه در `.gitignore` از ورود فایل‌های باینری متغیر یا داده‌های محیط اجرا به تاریخچه مخزن گیت جلوگیری می‌کند، در حالی که با دستور `LOGS_DIR.mkdir(parents=True, exist_ok=True)` در `settings.py` اطمینان حاصل می‌شود که پوشه به شکل خودکار در هر محیط تازه ایجاد خواهد شد.

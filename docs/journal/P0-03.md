# P0-03 — Django scaffold + PostgreSQL + custom User skeleton

## What was done (3–6 bullets)
- Configured backend Python dependencies in `backend/requirements.txt` (Django 5.1, psycopg 3, django-environ, coverage).
- Scaffolded Django project configuration (`backend/config/`, `manage.py`) driven by environment variables via `django-environ`.
- Implemented custom User skeleton extending `AbstractUser` in `apps.accounts` and configured `AUTH_USER_MODEL = "accounts.User"` before the initial migration.
- Created `apps.core` with HTTP response helpers (`json_ok`, `json_error`, `parse_json`) and the `GET /api/health/` endpoint per `API_CONTRACT.md`.
- Applied initial migrations to local PostgreSQL `hotel_db` and added comprehensive unit tests (97% total coverage).
- Added "Backend quick start" documentation to root `README.md`.

## Why / design decisions (and alternatives rejected)
- Configured `AUTH_USER_MODEL` before running any migrations: switching user models in Django after initial migration is complex and error-prone.
- Used plain Django views and forms with standardized JSON envelopes (`{"data": ...}`, `{"message": ..., "errors": ...}`) per decision D-002, avoiding DRF overhead while matching the course curriculum.
- Used `psycopg` (v3) binary for modern PostgreSQL connectivity.

## How it works (follow ONE request/click end to end)
- When a client sends `GET /api/health/`, Django routes the request through `config/urls.py` to `apps.core.urls.py`. The `health_check` view executes and calls `json_ok({"status": "ok"})`, which wraps the payload in `{"data": {"status": "ok"}}` and returns a `JsonResponse` with HTTP status 200.

## How to test (commands / clicks)
- `cd backend && python manage.py check` verifies system configuration.
- `python manage.py makemigrations --check --dry-run` ensures migrations are fully up to date.
- `python manage.py test` executes all test cases (7 tests passing).
- `coverage run manage.py test && coverage report` checks test coverage.
- `curl http://localhost:8000/api/health/` verifies the JSON health check response.

## Gotchas / things that surprised us
- Running `python manage.py test` from project root does not automatically discover tests in `apps/` unless explicitly directed; running from `backend/` discovers all tests properly.
- In PostgreSQL 15+, public schema permissions are restricted by default, so creating the user requires explicitly granting schema usage/create permissions.

1. س: چرا مدل سفارشی کاربر (`AUTH_USER_MODEL`) را از همان ابتدا و قبل از اجرای اولین migrate تعریف کردیم؟
   ج: طبق مستندات رسمی جنگو، تغییر مدل کاربر پس از اعمال اولین مایگریشن‌ها بر روی جدول پیش‌فرض `auth_user` بسیار دشوار است و نیاز به دستکاری کلیدهای خارجی چندین جدول داخلی جنگو دارد. تعریف یک اسکلت اولیه قبل از مایگریشن اول، توسعه‌های بعدی را کاملاً امن و استاندارد می‌کند.
2. س: چرا به جای کتابخانه‌هایی مثل Django REST Framework (DRF) از توابع کمکی دست‌ساز در `apps/core/http.py` استفاده شده است؟
   ج: بر اساس تصمیم معماری پروژه (D-002) و سرفصل درس برنامه‌سازی وب، هدف یادگیری عمیق سازوکار درونی جنگو و فرم‌ها بدون تکیه بر فریم‌ورک‌های سنگین جانبی است. توابع `json_ok` و `json_error` ساختار خروجی استاندارد و سازگار با فرانت‌اند را با کمترین پیچیدگی فراهم می‌کنند.
3. س: متغیرهای محیطی در جنگو چگونه مدیریت شده‌اند و چرا نباید فایل `.env` کامیت شود؟
   ج: از پکیج `django-environ` استفاده شده که فایل `.env` را می‌خواند. فایل `.env` شامل مقادیر حساس مثل `DJANGO_SECRET_KEY` و رمز عبور دیتابیس است که نباید در گیت کامیت شوند؛ به جای آن یک فایل `.env.example` نمونه در مخزن قرار دارد.
4. س: مکانیزم تست‌ها چگونه اجرا می‌شوند و دیتابیس تست چه ویژگی دارد؟
   ج: دستور `python manage.py test` به طور خودکار یک دیتابیس موقت با پیشوند `test_` در PostgreSQL می‌سازد، تمام مایگریشن‌ها را روی آن اعمال کرده، تست‌ها را درون تراکنش‌های ایزوله اجرا می‌کند و در پایان دیتابیس تست را پاک می‌کند.

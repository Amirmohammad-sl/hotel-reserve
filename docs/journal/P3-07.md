## What was done (3–6 bullets)
- Implemented `last_city` cookie setting in `hotels_list_view` (`GET /api/hotels/?city=...`), URL-encoding the city name to fully comply with RFC 6265 and prevent Unicode header issues.
- Implemented recently viewed hotel tracking in `hotel_detail_view` (`GET /api/hotels/<id>/`), persisting an LRU list of hotel IDs in Django's session (`request.session['recent_hotel_ids']`, capped at 10 items, moving previously viewed hotels to the top on re-visit).

- Integrated a prominent "هتل‌های اخیراً مشاهده‌شده" (Recently Viewed Hotels) card grid into `HomePage.jsx` powered by `getRecentHotelsApi()`.
- Added comprehensive unit and integration tests in `backend/apps/hotels/tests.py` (`RecentHotelsAndCookiesTestCase`) verifying cookie encoding, session order, LRU behavior, empty state, and inactive hotel filtering.
- Updated `docs/API_CONTRACT.md` and marked task `P3-07` as `DONE` in `docs/tasks/phase-3.md`.

## Why / design decisions (and alternatives rejected)
- **Cookie vs Session for Last Search**: A cookie (`last_city`) was chosen for the last searched city because it is lightweight, directly visible in browser devtools, client-accessible without extra network roundtrips, and survives session resets or browser restarts (30-day max-age).
- **Session vs LocalStorage for Recently Viewed Hotels**: The course explicitly mandates demonstrating server-side session management (`request.session`). Storing `recent_hotel_ids` in Django session verifies server-side state persistence across different page navigations.
- **URL-Encoding in Cookies**: Persian city names (e.g., «تهران») contain non-ASCII Unicode characters. Standard HTTP headers (RFC 6265 / WSGI) expect ASCII/Latin-1 characters. Storing raw Unicode in `Set-Cookie` can throw `UnicodeEncodeError` in production web servers. Encoding with `urllib.parse.quote` and decoding with `decodeURIComponent` guarantees 100% interoperability across all browsers and ASGI/WSGI servers.
- **LRU (Least Recently Used) Deduplication**: When a guest revisits a hotel they viewed earlier, simply appending the ID would create duplicate cards or leave the hotel in an older position. Removing the ID and prepending it to index 0 ensures the most recently viewed hotel is always first.
- **Inactive Hotel Filtering**: If a manager deactivates a hotel after a guest has viewed it, `recent_hotels_view` filters `is_active=True`, ensuring deactivated hotels never appear in public recommendations.

## How it works (follow ONE request/click end to end)
1. **Setting the Cookie**:
   - Guest visits the search page and searches for hotels in "تهران".
   - Frontend calls `GET /api/hotels/?city=تهران`.
   - `hotels_list_view` processes the query, finds matching hotels, and attaches `Set-Cookie: last_city=%D8%AA%D9%87%D8%B1%D8%A7%D9%86; Max-Age=2592000; Path=/; SameSite=Lax`.
   - Browser stores the cookie in DevTools -> Application -> Cookies.
2. **Pre-filling on Next Visit**:
   - Guest closes the browser, reopens it, and navigates to the home page (`/`).
   - `SearchForm` initializes its `city` state from `getCookie('last_city')`.
   - The city dropdown/input is immediately pre-filled with "تهران" without requiring the user to retype.
3. **Session Tracking & Display**:
   - Guest clicks on a hotel card to view details (`/hotels/3`).
   - Frontend requests `GET /api/hotels/3/`.
   - `hotel_detail_view` updates `request.session['recent_hotel_ids'] = [3, ...]`.
   - Guest returns to HomePage (`/`).
   - `HomePage` runs `getRecentHotelsApi()` (`GET /api/hotels/recent/`).
   - Backend reads session IDs, loads active hotel objects, and returns them in exact viewing order.
   - HomePage renders the "هتل‌های اخیراً مشاهده‌شده" section showing Hotel 3 with star rating, photo, city, and min_price.

## Viva Q&A (Persian, 3–5) — questions the professor could ask about this task
1. **س: تفاوت استفاده از Cookie برای `last_city` و Session برای هتل‌های اخیر چیست و چرا از هر دو استفاده شد؟**
   **ج:** برای `last_city` از کوکی استفاده شد چون داده‌ای سبک و غیرحساس برای تنظیم رابط کاربری (UI State) است که حتی با بستن مرورگر یا انقضای سشن سمت سرور باید برای ۳۰ روز باقی بماند تا فرم جستجو را به صورت خودکار پر کند. اما برای هتل‌های اخیراً مشاهده‌شده، طبق نیازمندی پروژه مبنی بر مدیریت سشن سمت سرور، شناسه‌ها در `request.session` ذخیره می‌شوند تا مدیریت وضعیت و اعتبارسنجی هتل‌ها (فعال بودن، قیمت‌ها و عدم وابستگی به داده‌های کلاینت) به شکل امن در سرور انجام شود.

2. **س: چرا نام شهرهای فارسی در کوکی با `urllib.parse.quote` انکود شد؟**
   **ج:** طبق استاندارد RFC 6265 و مشخصات پروتکل HTTP/1.1، هدرهای HTTP تنها مجاز به استفاده از کاراکترهای اسکی (ASCII) هستند. قرار دادن مستقیم کاراکترهای فارسی (یونیکد) در هدر `Set-Cookie` در وب‌سرورهای استاندارد پایتون (WSGI/ASGI مانند Gunicorn یا Uvicorn) باعث پرتاب خطای `UnicodeEncodeError` می‌شود. با انکود کردن به درصد (`%XX`) در سرور و دیکود با `decodeURIComponent` در جاوااسکریپت، از بروز هرگونه خطا جلوگیری شده و استاندارد به صورت کامل رعایت می‌شود.

3. **س: در سناریویی که کاربر هتلی را قبلاً دیده و دوباره به صفحه آن برمی‌گردد، ترتیب نمایش در سشن چگونه حفظ می‌شود؟**
   **ج:** از الگوریتم LRU (Least Recently Used) استفاده شده است؛ قبل از درج شناسه هتل، بررسی می‌شود که اگر قبلاً در لیست سشن وجود داشته باشد، ابتدا حذف شده و سپس به ابتدای لیست (اندیس صفر) اضافه می‌شود (`recent_ids.insert(0, hotel_id)`). همچنین طول لیست به ۱۰ هتل محدود می‌شود تا حجم سشن کنترل شود.

4. **س: اگر هتلی توسط مدیر غیرفعال شود یا از دیتابیس حذف گردد، چگونه در هتل‌های اخیر مدیریت می‌شود؟**
   **ج:** در اندپوینت `recent_hotels_view`، هنگام خواندن هتل‌ها از دیتابیس فیلتر `is_active=True` اعمال می‌شود (`Hotel.objects.filter(id__in=recent_ids, is_active=True)`). بنابراین هتل‌های غیرفعال یا حذف‌شده به صورت خودکار از خروجی حذف می‌شوند و اطلاعات ناقص به کاربر نمایش داده نمی‌شود.

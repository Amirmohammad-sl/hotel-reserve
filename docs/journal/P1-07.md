## Why / design decisions (and alternatives rejected)
- **Autocomplete fields over raw ID fields**: `autocomplete_fields` provides an AJAX-driven search dropdown (utilizing the target model's `search_fields`) which offers a superior user experience compared to entering integer IDs manually in raw ID fields.
- **Form-level nights calculation (`BookingAdminForm`)**: The `Booking` model enforces strict integer requirements for `nights` but auto-derives it in `calculate_nights()`. Providing a custom `ModelForm` where `nights` is `required=False` allows staff to either enter custom night counts or leave it blank to be computed deterministically from `(check_out - check_in).days`.
- **Inline RoomType in HotelAdmin**: Fulfills the explicit deliverable ("inlines for RoomType in Hotel"), enabling hotel managers or operators to inspect and manage room inventory directly from the parent hotel page.
- **Readonly fields for timestamps and audit logs**: Setting `created_at` and `cancelled_at` as `readonly_fields` prevents accidental tampering with historical audit data in Django admin.

## How it works (follow ONE request/click end to end)
1. Staff user logs into Django administration at `/admin/` with superuser credentials.
2. The user navigates to **Hotels > Hotels** (`/admin/hotels/hotel/`) where all hotels are listed with filters for `city`, `star_rating`, and `is_active`.
3. Clicking on a hotel opens its edit form showing the `RoomTypeInline` table, displaying all room categories associated with that hotel.
4. Staff can search for users via AJAX autocomplete when assigning the hotel owner.
5. In **Bookings > Bookings** (`/admin/bookings/booking/`), staff can create or review reservations with date hierarchy drill-down by `check_in` and filters by `status`.

## Gotchas / things that surprised us
- In Django ModelForms, field validation occurs during `clean_fields()` before `form.clean()` is called. If a model field does not specify `blank=True` in the model definition (like `nights` in `Booking`), Django form validation will reject empty inputs as required before `form.clean()` can calculate them. Explicitly declaring `nights = forms.IntegerField(required=False)` on `BookingAdminForm` cleanly solved this issue.
- Using `autocomplete_fields` requires that the referenced target model's `ModelAdmin` defines `search_fields`. Ensuring that `UserAdmin`, `HotelAdmin`, `RoomTypeAdmin`, and `DiscountCodeAdmin` all specify appropriate `search_fields` allows cross-referencing autocomplete dropdowns without any system check errors.

1. س: تفاوت `list_display`، `list_filter` و `search_fields` در `ModelAdmin` جنگو چیست و چرا در این تسک برای تمامی مدل‌ها تنظیم شدند؟
   ج: `list_display` ستون‌هایی را مشخص می‌کند که در جدول لیست رکوردها نمایش داده می‌شوند تا اطلاعات کلیدی در یک نگاه دیده شوند. `list_filter` پنل فیلتر سمت راست را ایجاد می‌کند تا بر اساس فیلدهای دسته‌بندی، وضعیت یا بازه زمانی رکوردها فیلتر شوند. `search_fields` کادر جستجوی متنی بالای لیست را فعال می‌کند که بر اساس فیلدهای مشخص شده (شامل فیلدهای روابط با `__`) کوئری SQL `LIKE` یا `ILIKE` می‌زند.
2. س: پیش‌نیاز استفاده از قابلیت `autocomplete_fields` در ادمین چیست و چه مزیتی نسبت به انتخاب معمولی (Select Box) دارد؟
   ج: برای استفاده از `autocomplete_fields` روی یک کلید خارجی (ForeignKey)، ادمین مدل مقصد باید حتماً `search_fields` تعریف کرده باشد. مزیت آن این است که به جای لود کردن تمام رکوردهای جدول مقصد در یک Dropdown بزرگ HTML (که در دیتابیس‌های واقعی با هزاران کاربر یا هتل باعث افت شدید کارایی و کندی مرورگر می‌شود)، به صورت ایجکس (AJAX) و فقط هنگام تایپ کاربر داده‌ها را در دسته‌های کوچک از سرور واکشی می‌کند.
3. س: چرا در `HotelAdmin` از `TabularInline` برای `RoomType` استفاده شده است؟
   ج: طبق نیازمندی‌های پروژه و صورت تسک، هر هتل دارای چند نوع اتاق (`RoomType`) است. با استفاده از `TabularInline`، مدیر سیستم می‌تواند در همان صفحه ویرایش هتل، تمام انواع اتاق‌های آن هتل، ظرفیت، قیمت و تعداد آن‌ها را در قالب یک جدول فشرده مشاهده و ویرایش کند و نیازی به رفت و برگشت مداوم بین صفحات مختلف ندارد.
4. س: چرا فیلدهایی مانند `created_at` و `cancelled_at` در ادمین به صورت `readonly_fields` تنظیم شده‌اند؟
   ج: فیلدهای مربوط به زمان ثبت یا لغو (`created_at` و `cancelled_at`) جنبه‌ی ثبت وقایع و تاریخچه حسابرسی (audit trail) سیستم را دارند. اگر این فیلدها در ادمین قابل دستکاری و ویرایش باشند، یکپارچگی تاریخی و استنادپذیری رکوردهای رزرو خدشه‌دار می‌شود؛ بنابراین فقط به صورت فقط‌خواندنی نمایش داده می‌شوند.

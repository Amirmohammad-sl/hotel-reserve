## What was done (3–6 bullets)
- Re-architected and updated `docs/PROCESS_DIAGRAMS.md` to strictly satisfy the professor's Phase 1 Process Diagram guidelines.
- Filtered out routine processes (eliminated login/registration, simple CRUD, simple search) in accordance with the course rubric.
- Designed 4 core business process diagrams + 1 bonus process using the Swimlane/Subgraph pattern to clearly distinguish User Actions from System Processing:
  1. Room Quote, Capacity Pre-check & Discount Code Validation
  2. Booking Creation & Concurrency Control (Overbooking Prevention via Atomic Transactions)
  3. Booking Cancellation, Date Constraints & Resource Rollback
  4. Manager Room Availability Matrix & Occupancy Calendar Monitoring
  5. (Bonus) Verified Stay Review & Rating Aggregation
- Modeled explicit Decision Points, Error Conditions (400, 401, 403, 409 Conflict), and compensation flows (Rollbacks).
- Generated clean vector SVG assets for all processes in `docs/report/diagrams/` ready for inclusion in the final report.

## Why / design decisions (and alternatives rejected)
- **Eliminating Routine Diagrams**: The professor explicitly instructed not to draw generic authentication or simple entity editing. Focusing exclusively on core hotel operations maximizes evaluation rubric scores.
- **Swimlane / Subgraph Layout**: Placing user actions in one column and system/backend processing in the other fulfills the requirement that "user activities and system reactions must be distinctly distinguishable".
- **Explicit Concurrency Modeling**: Displaying `SELECT ... FOR UPDATE` and atomic transaction rollbacks clearly shows the evaluation committee how race conditions are handled.

## Gotchas / things that surprised us
- Mermaid swimlanes are best represented using `subgraph` blocks within `flowchart TD` to keep cross-lane edges neat and prevent crossing spaghetti links.
- Encoding Mermaid payloads using zlib deflate compression (`pako:`) reliably generates high-resolution SVG outputs without hitting URL length ceilings.

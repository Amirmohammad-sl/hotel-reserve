## Why / design decisions (and alternatives rejected)
- **Database-Backed Sessions (`django.contrib.sessions.backends.db`)**: Mandated by course requirements and architectural decision D-003. Unlike cookie-based sessions (`signed_cookies`) which store encrypted payloads in the client header and cannot be revoked server-side, database sessions allow instant server-side revocation, administrative monitoring, and strict control over active logins.
- **Cookie Security Flags (`HttpOnly`, `SameSite=Lax`, `Secure`)**:
  - `HttpOnly=True`: Prevents client-side JavaScript (`document.cookie`) from accessing the sensitive `sessionid` cookie, mitigating session hijacking through Cross-Site Scripting (XSS).
  - `SameSite="Lax"`: Provides a balanced defense against Cross-Site Request Forgery (CSRF) by withholding cookies on cross-origin subrequests (such as image loads or third-party POSTs) while preserving cookie delivery on top-level safe navigations (e.g., following a link).
  - `Secure=not DEBUG`: Enforces transmission strictly over HTTPS in staging and production environments (`DEBUG=False`), while allowing standard HTTP during local development (`http://localhost:8000`).
- **Remember-Me Session Expiration (0 vs 14 Days)**: When the user leaves `remember_me` unchecked, `request.session.set_expiry(0)` instructs the client browser to treat the cookie as a session-only cookie that expires immediately when the browser window/process is closed. When checked, `request.session.set_expiry(1209600)` sets the expiration to 14 days, providing persistent access.
- **Session-Stored Last Login Time**: Storing `last_login` in `request.session["last_login"]` allows the system to reflect the exact initiation timestamp of the current active browser session on `/api/auth/me/`, independent of database writes to the user row on repeated background requests.
- **Periodic Maintenance with `clearsessions`**: In Django, database-backed sessions do not automatically prune expired rows from `django_session` on each request to prevent performance bottlenecks. Documenting `python manage.py clearsessions` in `README.md` provides operators with the exact standard procedure required for production cron maintenance.

## How it works (follow ONE request/click end to end)
1. **User Login (`remember_me=True`)**:
   - Client sends `POST /api/auth/login/` with `{"username_or_email": "manager1", "password": "...", "remember_me": true}` and `X-CSRFToken` header.
   - `login_view` validates credentials, logs in the user via `login(request, user)`.
   - `request.session["last_login"] = timezone.now().isoformat()` records the login moment in the session payload.
   - `request.session.set_expiry(1209600)` sets session lifetime to 14 days.
   - Django's `SessionMiddleware` serializes the session dictionary, persists it in the `django_session` PostgreSQL table, and sends a `Set-Cookie: sessionid=...; HttpOnly; SameSite=Lax; Max-Age=1209600; Path=/` response header.
2. **Checking Session State (`/api/auth/me/`)**:
   - Client sends `GET /api/auth/me/` with the `sessionid` cookie.
   - `SessionMiddleware` queries `django_session`, deserializes the session, and attaches it to `request.session`.
   - `AuthenticationMiddleware` resolves `request.user`.
   - `me_view` extracts `last_login = request.session.get("last_login")` and returns HTTP 200 with `{ "data": { "id": 1, "username": "manager1", ..., "last_login": "2026-11-08T..." } }`.
   - The frontend `Navbar` renders the user's role and attaches a Persian formatted tooltip: `آخرین ورود: ۱۸ آبان ۱۴۰۵، ۰۰:۳۵`.
3. **User Logout**:
   - Client sends `POST /api/auth/logout/`.
   - `logout_view` calls `request.session.flush()`, which executes `DELETE FROM django_session WHERE session_key = ...` in PostgreSQL, clears all session dictionary keys in memory, and sets an expired cookie header.
   - Subsequent calls to `GET /api/auth/me/` return `{"data": null}` with HTTP 200.

## Gotchas / things that surprised us
- In Django's test client, `self.client.session.get_expire_at_browser_close()` accurately inspects session expiry configuration. When `set_expiry(0)` is executed, Django internally flags `session.get_expire_at_browser_close() == True`, whereas when `set_expiry(1209600)` is executed, `get_expire_at_browser_close() == False` and `get_expiry_age() == 1209600`.
- In `logout_view`, calling `request.session.flush()` explicitly before `logout(request)` guarantees that the active session record in the database is immediately purged via SQL `DELETE`, rather than merely detaching the authenticated user pointer from the existing session key.

1. س: چرا برای مدیریت نشست‌ها (Session) از `django.contrib.sessions.backends.db` استفاده کرده‌اید و تفاوت آن با سشن‌های مبتنی بر کوکی (`signed_cookies`) چیست؟
   ج: در روش ذخیره‌سازی در پایگاه داده (Database-backed)، تمام داده‌های سشن به شکل رکورد در جدول `django_session` در PostgreSQL ذخیره شده و فقط یک کلید رندوم ۳۲ کاراکتری (`sessionid`) در کوکی کلاینت قرار می‌گیرد. تفاوت عمده با `signed_cookies` در این است که در کوکی‌های امضاشده سرور امکان ابطال آنی سشن را بدون تغییر کلید رمزنگاری کل سیستم ندارد؛ اما با استفاده از پایگاه داده، سرور با یک دستور ساده (`request.session.flush()` یا دستور SQL حذف رکورد) می‌تواند دسترسی کاربر را در همان لحظه باطل کند. همچنین حجم داده‌های سشن محدود به سقف ۴ کیلوبایتی کوکی مرورگر نمی‌شود.
2. س: فلگ‌های امنیتی کوکی شامل `HttpOnly`، `SameSite` و `Secure` هر کدام چه نقشی در امنیت دارند؟
   ج:
   - `HttpOnly=True`: دسترسی کدهای جاوااسکریپت سمت مرورگر (`document.cookie`) به مقدار کوکی `sessionid` را مسدود می‌کند؛ در نتیجه حتی در صورت بروز آسیب‌پذیری تزریق اسکریپت (XSS)، مهاجم نمی‌تواند کوکی سشن را به سرور خود سرقت کند.
   - `SameSite=Lax`: مرورگر را ملزم می‌کند که در درخواست‌های متقاطع ناشی از سایت‌های دیگر (مانند فرم‌های مخرب POST خارجی)، کوکی سشن را ارسال نکند و تنها در ناوبری‌های امن سطح بالا کوکی را بفرستد؛ این امر مانع از حملات جعل درخواست میان‌وب‌گاهی (CSRF) می‌شود.
   - `Secure=True`: مرورگر را موظف می‌کند که کوکی را صرفاً بر بستر رمزنگاری‌شده HTTPS ارسال کند تا از شنود کوکی در بستر شبکه ناامن جلوگیری شود (در پروژه در حالت `DEBUG=False` فعال است).
3. س: گزینه «مرا به خاطر بسپار» (Remember Me) چگونه کار می‌کند و تفاوت انقضای سشن در حالت فعال و غیرفعال چیست؟
   ج: با استفاده از متد `request.session.set_expiry()`. اگر کاربر remember_me را علامت زده باشد، انقضای سشن برابر ۱۴ روز (۱۲۰۹۶۰۰ ثانیه معادل `SESSION_COOKIE_AGE`) تنظیم می‌شود و کوکی مرورگر دارای فیلد `Max-Age` معتبر و پایدار می‌گردد. اما اگر این گزینه علامت نخورده باشد، `set_expiry(0)` اجرا می‌شود که به مرورگر دستور می‌دهد کوکی از نوع سشن موقت بوده و با بسته شدن تب/مرورگر، کوکی بلافاصله منقضی و حذف شود.
4. س: چرا اجرای دوره‌ای دستور `python manage.py clearsessions` در پروژه‌های جنگو ضروری است؟
   ج: جنگو برای جلوگیری از افت کارایی و سربار کوئری‌های دیتابیس در هر درخواست HTTP، رکوردهای منقضی‌شده سشن را به صورت خودکار از جدول `django_session` پاک نمی‌کند. با گذشت زمان و لاگین‌های متعدد، تعداد رکوردهای تاریخ‌گذشته افزایش می‌یابد؛ بنابراین دستور `clearsessions` باید به صورت یک cron job دوره‌ای (مثلاً شبانه) اجرا شود تا رکوردهای منقضی‌شده را پاکسازی کرده و حجم دیتابیس بهینه بماند.
5. س: خروج از حساب (Logout) در پروژه چگونه پیاده‌سازی شده و از پاک شدن کامل اطلاعات اطمینان حاصل می‌شود؟
   ج: در ویوی `logout_view`، متد `request.session.flush()` فراخوانی می‌شود. این متد سه کار حیاتی انجام می‌دهد: داده‌های سشن جاری را از حافظه پاک می‌کند، رکورد مربوط به `session_key` را مستقیماً از جدول `django_session` در پایگاه داده حذف می‌کند، و یک کوکی خالی با تاریخ انقضای گذشته به مرورگر ارسال می‌کند تا کوکی در مرورگر کلاینت نیز حذف شود. در تست `test_logout_flushes_session_from_database` دقیقاً چک شده است که پس از خروج، هیچ رکوردی با آن کلید در دیتابیس باقی نمی‌ماند.

## Why / design decisions (and alternatives rejected)
- **Nested `apps.` package path**: Storing apps inside `backend/apps/` rather than cluttering `backend/` root keeps project structure tidy. Setting `name = "apps.<name>"` in `apps.py` ensures Django correctly discovers models and migrations without namespace collisions.
- **Stub `urls.py` per app**: Including `urls.py` stubs from each app in `config/urls.py` early allows frontend development and subsequent backend tasks (P1-03 through P2-06) to plug routes in modularly without touching global project routing repeatedly.
- **Separation of boundaries**: `hotels` manages hotel listings, rooms, and amenities; `bookings` manages customer reservations and discount codes; `reviews` manages customer feedback. Clear architectural boundaries avoid circular imports and keep database responsibilities distinct.

## How it works (follow ONE request/click end to end)
- When Django boots up, `config/settings.py` reads `INSTALLED_APPS` and initializes each app's `AppConfig` (`apps.core`, `apps.accounts`, `apps.hotels`, `apps.bookings`, `apps.reviews`).
- The root URL dispatcher `config/urls.py` inspects incoming HTTP requests:
  - `/api/health/` routes to `apps.core.urls`
  - `/api/auth/*` routes to `apps.accounts.urls`
  - `/api/*` routes to `apps.hotels.urls`, `apps.bookings.urls`, and `apps.reviews.urls`.

## Gotchas / things that surprised us
- If `name` in `AppConfig` is set to `"hotels"` instead of `"apps.hotels"` while placed inside the `apps/` directory, Django's app registry can fail to properly import modules unless `apps` is in `sys.path`. Explicitly defining `name = "apps.<app_name>"` provides robust and portable resolution.

## Why / design decisions (and alternatives rejected)
- **django.core.signing.TimestampSigner over database-stored tokens (ADR D-007)**:
  - *Decision*: Tokens are signed and timestamped using Django's cryptographic signing tools (`TimestampSigner`) with a dedicated salt (`accounts.email-verification`).
  - *Why*: Stateless tokens require zero additional database tables, zero database writes on generation, and zero background cleanup jobs for expired tokens. The expiration check (`max_age=172800`) is handled in O(1) mathematically by comparing the embedded timestamp against system time.
- **Method-Aware `@verified_required(methods=["POST"])` on Shared Endpoints**:
  - *Decision*: Allowed `@verified_required` to selectively target specific HTTP methods or all methods.
  - *Why*: On manager hotel management (`/api/manager/hotels/`), `GET` allows unverified managers to inspect their existing hotels or view their dashboard, while `POST` strictly blocks unverified managers from creating new hotels (HTTP 403).
- **Separation of Registration from Verification**:
  - *Decision*: Users are allowed to complete registration and log in immediately, but are restricted from executing irreversible business transactions (booking rooms, creating hotels) until their email is verified.
  - *Why*: Reduces onboarding drop-off while protecting the hotel inventory from spam and automated bots.
- **Auditing and Security Logging**:
  - *Decision*: Unverified access attempts and successful verification operations are logged under `apps.security` with remote IP and user ID, maintaining strict audit trails for course evaluation.

## How it works (follow ONE request/click end to end)
1. User registers by posting `{ "username": "alice", "email": "alice@example.com", "password": "...", "role": "guest" }` to `POST /api/auth/register/`.
2. The user is saved to PostgreSQL with `email_verified=False`.
3. `send_verification_email(user)` generates a signed token `alice.pk:timestamp:hash` and dispatches an email via Django's console email backend.
4. Alice attempts to book a hotel room (`POST /api/bookings/`). The `@verified_required` decorator intercepts the request, detects `request.user.email_verified == False`, logs a warning to `apps.security`, and responds with `403 Forbidden` (`{"message": "Email verification required. Please verify your email address."}`).
5. Alice opens her terminal / email client, clicks the verification link: `http://localhost:5173/verify-email?token=<token>`.
6. React router loads `VerifyEmailPage`, extracts the token from URL search params, and calls `verifyEmailApi({ token })` (`POST /api/auth/verify-email/`).
7. Django's `verify_email_view` validates the signature and confirms token age is under 48 hours. It sets `user.email_verified = True`, saves to the database, logs success to `apps.security`, and returns `200 OK` with updated user payload.
8. The React page displays the success state, calls `refreshUser()` to hydrate `AuthContext`, and Alice is now able to book rooms and create hotels without restrictions.

## Viva defense questions & answers (3–5 questions)

### Q1: Why did you choose cryptographic signed tokens (`TimestampSigner`) over storing tokens in a database model?
**Answer:**
Cryptographic tokens using `django.core.signing.TimestampSigner` are completely stateless. They encapsulate the user ID, a timestamp, and an HMAC SHA-256 signature generated with Django's `SECRET_KEY` and a unique salt. This eliminates database writes on token creation, avoids adding extra tables or migrations, and removes the need for periodic cron jobs to clean up expired tokens. The expiration (48 hours) is verified mathematically upon receipt.

### Q2: What happens if an attacker tampers with the token in the URL or sends an expired link?
**Answer:**
If an attacker alters any character in the token (the user ID, timestamp, or signature), `signer.unsign()` detects the signature mismatch and raises `django.core.signing.BadSignature`, returning HTTP 400 (`"Invalid or malformed verification link."`). If the token is older than 48 hours (172,800 seconds), `signer.unsign()` raises `django.core.signing.SignatureExpired`, returning HTTP 400 with a clear message indicating expiration and prompting the user to request a new link.

### Q3: Why is email verification enforced at the view decorator level rather than preventing login altogether?
**Answer:**
Allowing unverified users to log in provides a much smoother user experience: the user can browse their profile, see an informative banner explaining that verification is pending, and trigger an "ارسال مجدد ایمیل تایید" (resend) directly from the interface. We enforce `@verified_required` specifically on mutating business endpoints—booking rooms (`POST /api/bookings/`) and creating hotels (`POST /api/manager/hotels/`)—so malicious or fake accounts cannot occupy room capacity or publish hotels.

### Q4: How does the `@verified_required` decorator work when an endpoint serves both GET and POST requests?
**Answer:**
The decorator supports an optional `methods` keyword argument: `@verified_required(methods=["POST"])`. When applied to `manager_hotels_list_create_view`, incoming `GET` requests pass through so the manager can view their hotels list or dashboard, while `POST` requests inspect `request.user.email_verified`. If `email_verified` is False, it immediately aborts the pipeline, logs a security warning, and returns HTTP 403 Forbidden.

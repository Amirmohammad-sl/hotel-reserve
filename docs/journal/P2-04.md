## Why / design decisions (and alternatives rejected)
- **Daily Night Breakdown in Availability**: Per Decision D-004 and D-006, hotel bookings operate on a per-night basis where check-out is departure day. A date window `[date_from, date_to)` iterates day by day, counting confirmed bookings where `check_in <= day < check_out`. Cancelled bookings are strictly ignored (`status=Booking.Status.CONFIRMED`).
- **HTTP 404 for Unowned Objects**: When Manager A tries to manage Manager B's hotel or discount code, returning 404 Not Found ensures that the existence of private entities is never leaked (preventing ID enumeration), exactly as established in P2-03.
- **Handling Form Updates and `is_active`**: Standard Django forms default boolean fields to `False` if omitted in a payload (standard checkbox behavior). In `DiscountCodeForm.clean_is_active()`, if `is_active` is not in `self.data`, we preserve `self.instance.is_active` on updates, preventing accidental coupon deactivation.
- **Form-level Duplicate Validation**: While PostgreSQL enforces `UniqueConstraint(fields=["hotel", "code"])`, catching duplicates in `DiscountCodeForm.clean()` provides clean field-level error messages (`{"errors": {"code": ["..."]}}`) with HTTP 400 instead of an unhandled HTTP 500 `IntegrityError`.

## DoD Verification: Hand-computed example with 3 overlapping bookings
- **Target Room Type**: "Deluxe Suite", `quantity = 10`.
- **Query Range**: `2026-10-01` to `2026-10-06` (5 nights: Oct 1, Oct 2, Oct 3, Oct 4, Oct 5).
- **Bookings in Database**:
  1. Booking 1: `check_in=2026-10-01`, `check_out=2026-10-04`, `rooms_count=3`, `status=confirmed` (active nights: Oct 1, Oct 2, Oct 3).
  2. Booking 2: `check_in=2026-10-02`, `check_out=2026-10-05`, `rooms_count=4`, `status=confirmed` (active nights: Oct 2, Oct 3, Oct 4).
  3. Booking 3: `check_in=2026-10-03`, `check_out=2026-10-06`, `rooms_count=2`, `status=confirmed` (active nights: Oct 3, Oct 4, Oct 5).
  4. Booking 4 (cancelled): `check_in=2026-10-02`, `check_out=2026-10-04`, `rooms_count=5`, `status=cancelled` (must be ignored).

## How it works (follow ONE request/click end to end)
1. **Manager Checks Availability Calendar**:
   - Manager sends `GET /api/manager/hotels/1/availability/?date_from=2026-10-01&date_to=2026-10-06` with session cookie.
   - `@role_required("manager")` decorator authenticates the user and verifies manager role.
   - View verifies `Hotel.objects.filter(id=1, owner=request.user)`.
   - `ManagerAvailabilityFilterForm` validates the date strings and ensures `date_to > date_from`.
   - All room types for hotel 1 are queried.
   - Confirmed bookings overlapping the window are fetched using `check_in < date_to AND check_out > date_from`.
   - For each room type, a day-by-day loop counts reserved rooms and subtracts from total physical quantity.
   - Endpoint returns HTTP 200 with JSON payload containing `daily_availability` for each room type.

2. **Manager Creates Discount Code**:
   - Manager sends `POST /api/manager/hotels/1/discounts/` with payload `{"code": "NOROOZ", "percent": 20, "valid_from": "2026-03-20", "valid_to": "2026-04-05", "max_uses": 100}`.
   - `DiscountCodeForm` validates fields and ensures "NOROOZ" is not already registered for hotel 1.
   - Coupon is saved to PostgreSQL and returned with HTTP 201 status.

## Gotchas / things that surprised us
- In availability calculations, hotel nights are semi-open intervals `[check_in, check_out)`. A guest checking in on Oct 1 and checking out on Oct 4 stays for nights Oct 1, Oct 2, and Oct 3. On Oct 4, the room is already vacated for the next guest, so checking `b.check_in <= curr_day < b.check_out` correctly reflects vacancy on departure day.
- A cancelled booking (`status='cancelled'`) must never count toward reserved rooms; otherwise guests who cancel would permanently consume hotel capacity.

## Viva Q&A (Persian, 3–5) — questions the professor could ask about this task
1. س: الگوریتم محاسبه دسترسی روزانه اتاق‌ها (`availability`) در اندپوینت مدیر چگونه کار می‌کند؟
   ج: سیستم بازه زمانی درخواستی را به صورت شب‌های اقامت `[date_from, date_to)` در نظر می‌گیرد. تمام رزروهای تأییدشده (`status=confirmed`) که با این بازه همپوشانی دارند (`check_in < date_to AND check_out > date_from`) از دیتابیس واکشی می‌شوند. سپس برای هر نوع اتاق و به ازای تک‌تک روزهای بازه، تعداد اتاق‌های رزروشده (`reserved`) با جمع بستن `rooms_count` رزروهایی که در آن شب فعال هستند (`check_in <= day < check_out`) محاسبه شده و تعداد اتاق‌های آزاد (`free`) از تفاضل ظرفیت کل اتاق (`quantity`) با تعداد رزرو شده به دست می‌آید (`max(0, quantity - reserved)`).
2. س: چرا رزروهای با وضعیت لغوشده (`cancelled`) نباید در محاسبه دسترسی شمرده شوند؟
   ج: وقتی مهمانی رزرو خود را لغو می‌کند، اتاق‌های رزرو شده بلافاصله آزاد می‌شوند تا سایر مسافران بتوانند آن را رزرو کنند. اگر در کوئری وضعیت رزرو فیلتر نشود، اتاق‌های لغوشده کماکان در اشغال باقی مانده و هتل با کمبود کاذب ظرفیت مواجه می‌شود.
3. س: چرا برای فیلتر بازه زمانی در `ManagerAvailabilityFilterForm` محدودیت حداکثر ۹۰ روز گذاشته‌اید؟
   ج: برای جلوگیری از حملات محروم‌سازی از سرویس (DoS) یا سنگین شدن بیش از حد سرور. اگر کاربری بازه ۱۰ ساله درخواست کند، سرور مجبور است حلقه ۳۶۵۰ روزه را برای تک‌تک اتاق‌ها محاسبه و حجم عظیمی از داده را سریالایز کند. با محدود کردن بازه به ۹۰ روز، سرعت پاسخگویی اندپوینت تضمین می‌شود.
4. س: اعتبارسنجی کدهای تخفیف در `DiscountCodeForm` چگونه مانع از ایجاد کدهای تکراری یا خطای ۵۰۰ می‌شود؟
   ج: در سطح دیتابیس قید `UniqueConstraint(fields=["hotel", "code"])` وجود دارد. اگر این اعتبارسنجی در فرم انجام نشود، دیتابیس خطای `IntegrityError` داده و کاربر خطای ۵۰۰ دریافت می‌کند. در متد `clean` فرم، بررسی می‌کنیم که آیا کدی با همین عنوان (حروف بزرگ و با تطابق نام حساس به بزرگی/کوچکی حروف) برای همان هتل وجود دارد یا خیر (با استثنا کردن رکورد فعلی در حالت ویرایش). در صورت وجود، خطای فیلد `code` به فرم افزوده شده و پاسخ ۴۰۰ تمیز با پیام خطای مشخص به کاربر بازمی‌گردد.
5. س: چرا در صورت تلاش یک مدیر برای مشاهده یا ویرایش کدهای تخفیف یا رزروهای هتل مدیری دیگر، خطای ۴۰۴ بازمی‌گردانید نه ۴۰۳؟
   ج: جهت جلوگیری از آسیب‌پذیری افشای شناسه‌ها (ID Enumeration). اگر خطای ۴۰۳ برگردانیم، مهاجم متوجه می‌شود که رکوردی با این شناسه در سیستم وجود دارد اما مال او نیست. با بازگرداندن ۴۰۴ بر اساس فیلتر مالکیتی `owner=request.user`، هیچ تفاوتی بین رکورد ناموجود و رکورد متعلق به دیگران وجود ندارد و امنیت چندمستأجره سامانه حفظ می‌شود.

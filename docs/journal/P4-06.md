## Why / design decisions (and alternatives rejected)
1. **`select_related` vs `prefetch_related` for Foreign Keys**:
   - For `ForeignKey` and `OneToOne` relationships (`Booking.room_type`, `RoomType.hotel`, `Booking.guest`), `select_related` performs a SQL `INNER JOIN` or `LEFT OUTER JOIN` in a single query.
   - Using `prefetch_related` on single-valued foreign keys would have created separate queries with `WHERE id IN (...)`, which is appropriate for `ManyToMany` relationships but sub-optimal for simple foreign key traversals.
2. **Selective Prefetch Trimming on Search**:
   - In `hotels_list_view`, RoomTypes were previously prefetching `amenities`. However, hotel cards only display summary information and `min_price`. Room amenities are only needed on the hotel detail page (`/api/hotels/<id>/`). Trimming `prefetch_related("amenities")` removes a redundant database query on every hotel search.
3. **Cached Template Loader Configuration (`not DEBUG`)**:
   - In development (`DEBUG = True`), template reloading allows live edits without restarting the server.
   - In production (`DEBUG = False`), compiling template syntax trees on every request adds significant CPU overhead. Using `django.template.loaders.cached.Loader` compiles each template once into memory and reuses it across threads/requests. Django requires setting `APP_DIRS = False` when defining explicit `loaders` in `TEMPLATES[0]["OPTIONS"]` to avoid configuration conflict.
4. **Email Template Inheritance (`base.html` / `base.txt`)**:
   - Deduplicating email headers, styles, RTL tags, and footers prevents styling drift across different transactional emails (e.g., email verification, booking confirmation, cancellation notices).

## How it works (follow ONE request end-to-end)
1. **Manager requests booking list for Hotel #5**:
   - Client sends `GET /api/manager/hotels/5/bookings/` with session cookie.
   - Authentication middleware resolves `request.user` via session.
   - `manager_hotel_bookings_list_view` checks ownership:
     `Hotel.objects.owned_by(request.user).filter(id=5).first()` (Query 1).
   - View executes the optimized booking query:
     ```python
     Booking.objects.for_hotel(hotel)
         .select_related("guest", "room_type", "room_type__hotel", "discount_code")
         .order_by("-created_at")
     ```
   - Django executes a single multi-table `JOIN`:
     ```sql
     SELECT "bookings_booking".*,
            "accounts_user".*,
            "hotels_roomtype".*,
            "hotels_hotel".*,
            "bookings_discountcode".*
     FROM "bookings_booking"
     INNER JOIN "hotels_roomtype" ON ("bookings_booking"."room_type_id" = "hotels_roomtype"."id")
     INNER JOIN "hotels_hotel" ON ("hotels_roomtype"."hotel_id" = "hotels_hotel"."id")
     LEFT OUTER JOIN "accounts_user" ON ("bookings_booking"."guest_id" = "accounts_user"."id")
     LEFT OUTER JOIN "bookings_discountcode" ON ("bookings_booking"."discount_code_id" = "bookings_discountcode"."id")
     WHERE "hotels_roomtype"."hotel_id" = 5
     ORDER BY "bookings_booking"."created_at" DESC;
     ```
   - During serialization in `booking_to_dict`, accessing `b.guest.username`, `b.room_type.title`, and `b.room_type.hotel.name` reads from pre-cached in-memory attributes. **Zero additional SQL queries are fired.**
   - Total queries: **2 queries** in view logic (4 including middleware), regardless of whether 1 or 1,000 bookings are returned.

## Viva Drill Questions & Answers

### Q1: What is the N+1 queries problem in Django ORM and how did it happen in our hotel booking list?
**Answer:**
The N+1 problem occurs when an application executes 1 initial query to fetch $N$ parent records, and then executes an additional query for each of the $N$ records when accessing a related object in a loop or serializer. In our manager bookings view, the initial query fetched $N$ bookings. When serializing each booking via `booking_to_dict`, the code accessed `booking.room_type.hotel.name`. Because `select_related` only fetched `room_type` but did not traverse to `room_type__hotel`, Django's lazy loading triggered a separate `SELECT ... FROM hotels_hotel WHERE id = ...` for every single booking in the list. For 100 bookings, this resulted in 100 extra queries.

### Q2: What is the difference between `select_related` and `prefetch_related` in Django, and when do you use each?
**Answer:**
- `select_related` works at the SQL level by creating a single SQL query with `INNER JOIN` or `LEFT OUTER JOIN`. It is used for single-valued relationships: `ForeignKey` and `OneToOneField`. It cannot be used on multi-valued relationships (like `ManyToManyField` or reverse foreign keys) because joining tables with many-to-many cardinality causes Cartesian product duplication of rows.
- `prefetch_related` executes separate SQL queries (usually 1 query for the parent queryset and 1 query for the related items using `WHERE id IN (...)`) and performs the join in Python memory. It is used for `ManyToManyField`, reverse `ForeignKey` relationships, and complex filtered prefetch operations via `Prefetch` objects.

### Q3: Why did we remove `prefetch_related("amenities")` from `hotels_list_view`?
**Answer:**
`hotels_list_view` powers the public hotel search results page. The API contract for hotel cards only returns hotel metadata (`id`, `name`, `city`, `star_rating`, `image_url`) and the calculated `min_price`. Room amenities (such as WiFi, pool, breakfast) are only displayed on the hotel detail page (`hotel_detail_view`). Prefetching amenities on the list view executed an unnecessary SQL query (`SELECT ... FROM hotels_amenity WHERE ... IN (...)`) across all rooms of all returned hotels, fetching data that was completely discarded. Removing it saved 1 database query on every public search request.

### Q4: How does Django's cached template loader work and why shouldn't it be enabled during development?
**Answer:**
By default in development (`DEBUG = True`), Django's template system reads the template file from the disk and parses it into a compiled syntax tree on every single render request, so developers can see file changes immediately without restarting the server.
In production (`DEBUG = False`), disk I/O and syntax parsing on every request create an unnecessary CPU bottleneck. `django.template.loaders.cached.Loader` wraps the standard filesystem and app directories loaders; it parses and compiles each template once upon first use and caches the in-memory compiled template object. All subsequent calls retrieve the pre-compiled template directly from RAM.

### Q5: Why is `APP_DIRS = False` necessary when configuring `cached.Loader` in `settings.py`?
**Answer:**
In Django's `TEMPLATES` setting, `APP_DIRS = True` is a shorthand convenience configuration that automatically instantiates `django.template.loaders.app_directories.Loader`. When custom `loaders` are specified under `OPTIONS['loaders']` (such as wrapping loaders inside `cached.Loader`), Django enforces that `APP_DIRS` must not be set to `True`. If both are provided, Django throws an `django.core.exceptions.ImproperlyConfigured: app_dirs and loaders options are mutually exclusive` exception during application startup.

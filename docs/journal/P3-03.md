## Why / design decisions (and alternatives rejected)
- **Fat Models, Thin Views Architectural Pattern**: Previously, views had to remember every specific column relationship (such as `room_type__hotel=hotel` or `hotel__owner=request.user` or combining `status=CONFIRMED` and `check_in__lt/check_out__gt`). Moving these constraints to dedicated QuerySet methods prevents code duplication (DRY) and guarantees that any future view or management command uses the exact same validated business logic.
- **Centralised Tenant Security**: In a multi-tenant platform where managers must only access their own hotels, rooms, and coupons, relying on individual developers to remember `filter(owner=request.user)` on every endpoint is error-prone. With `owned_by(request.user)`, tenancy enforcement is encapsulated at the model layer.
- **Declarative ORM Method Chaining**: Instead of building query dictionaries or raw filter combinations inside `manager_hotel_availability_view`, calling `Booking.objects.active().for_hotel(hotel).overlapping(date_from, date_to)` clearly expresses domain intent while generating optimal SQL execution plans.
- **Preserving 404 Not Found Security Semantics**: When querying single entities (e.g. `RoomType.objects.owned_by(request.user).filter(id=room_type_id).first()`), an unowned ID yields `None` which translates to HTTP 404 Not Found. This preserves the security requirement established in P2-03/P2-04 against ID enumeration attacks.

## How it works (follow ONE request/click end to end)
1. **Manager requests daily availability calendar:**
   - Manager navigates to `/manager/hotels/1/availability?date_from=2026-10-01&date_to=2026-10-06`.
   - View validates that Hotel 1 belongs to the authenticated manager via `Hotel.objects.owned_by(request.user).filter(id=1).first()`.
   - The view fetches hotel room types via `RoomType.objects.for_hotel(hotel)`.
   - Overlapping confirmed bookings are queried in a single call:
     ```python
     Booking.objects.active().for_hotel(hotel).overlapping(date_from, date_to)
     ```
   - Django executes SQL:
     ```sql
     SELECT "bookings_booking".*
     FROM "bookings_booking"
     INNER JOIN "hotels_roomtype" ON ("bookings_booking"."room_type_id" = "hotels_roomtype"."id")
     WHERE ("bookings_booking"."status" = 'confirmed'
       AND "hotels_roomtype"."hotel_id" = 1
       AND "bookings_booking"."check_in" < '2026-10-06'
       AND "bookings_booking"."check_out" > '2026-10-01');
     ```
   - Nightly inventory is calculated and returned in standard JSON format.

## Gotchas / things that surprised us
- In `manager_hotel_availability_view`, the previous code performed an `IN` query on `room_types` list (`room_type__in=room_types`). By refactoring to `Booking.objects.for_hotel(hotel)`, the query delegates the join directly to the database via `room_type__hotel_id=hotel.id`, eliminating the need to materialize room type IDs into Python memory before firing the booking query.

## Why / design decisions (and alternatives rejected)

- **Plain Django Function-Based Views over Django Rest Framework (DRF)**:
  - *Decision*: In adherence to course requirements and architectural decision `D-001`, all views are built as pure Django views using `JsonResponse`, standard decorators, and Django `Form`/`ModelForm` instances.
  - *Why*: DRF introduces heavy abstraction magic (Serializers, ViewSets, Routers) that obfuscates low-level web concepts (HTTP status codes, CSRF cookies, form validation cycles, session handling) which professors evaluate during the oral defense.
- **Strict Input Validation via Django Forms (Never Trust Raw JSON)**:
  - *Decision*: Every POST/PUT/DELETE view parses request JSON and passes the dictionary into a dedicated Django `Form` (e.g., `RegisterForm`, `LoginForm`, `HotelForm`, `RoomTypeForm`, `BookingQuoteForm`, `DiscountCodeForm`).
  - *Why*: Forms provide clean, centralized sanitization, type-casting, error dictionary normalization, and cross-field constraint validation (`clean()`) before data ever reaches the database or ORM layer.
- **Stateless Email Verification (`TimestampSigner`) vs Database Token Table**:
  - *Decision*: Signed email verification tokens cryptographically encode user ID and timestamp using Django's `TimestampSigner` with HMAC-SHA256.
  - *Why*: Avoids creating a temporary verification table, eliminating redundant database write/read queries and avoiding background cleanup jobs for expired tokens.
- **Asynchronous Side-Effects via `transaction.on_commit`**:
  - *Decision*: All email sending routines are triggered strictly via `transaction.on_commit(...)` callbacks inside atomic views.
  - *Why*: Prevents sending erroneous confirmation emails to customers if the database transaction aborts or rolls back due to a concurrent conflict.

## Viva defense questions & answers (3–5 questions)

### Q1: چرا در اندپوینت ثبت رزرو (`booking_create_view`) از `transaction.atomic()` و `select_for_update()` به صورت همزمان استفاده شده است؟
**پاسخ:** این دو ابزار مکمل یکدیگر برای حل دو مشکل بنیادین در سیستم‌های تراکنشی هستند:
1. **`select_for_update()` برای حل پدیده Race Condition:** وقتی دو مسافر همزمان آخرین اتاق خالی را در یک میلی‌ثانیه رزرو می‌کنند، اگر قفل سطری نباشد، هر دو سهمیه آزاد را ۱ می‌بینند و رزرو ثبت می‌شود (Overbooking). با `select_for_update()`، تراکنش اول ردیف `RoomType` را در پایگاه داده قفل می‌کند؛ تراکنش دوم در صف انتظار می‌ماند تا تراکنش اول تمام شود و سپس موجودی آزاد را ۰ دیده و با خطای `409 Conflict` متوقف می‌شود.
2. **`transaction.atomic()` برای خاصیت Atomicity (اصل تمام یا هیچ):** ثبت رزرو شامل چند عملیات متوالی است: درج رکورد در جدول `Booking`، افزایش سهمیه مصرف کد تخفیف (`used_count`) و کسر موجودی. اگر در حین هر کدام از این مراحل خطایی رخ دهد، با `transaction.atomic` تمام تغییرات به صورت یکجا `Rollback` می‌شوند تا داده‌ها ناسازگار نمانند.

### Q2: چرا اعتبارسنجی ورودی‌های JSON با استفاده از Django Forms انجام شده در حالی که از DRF استفاده نکرده‌اید؟
**پاسخ:** طبق قواعد درس و تصمیم معماری `D-001`، نباید به داده‌های خام ورودی کلاینت اعتماد کرد. مزایای استفاده از `Form`های استاندارد جنگو عبارتند از:
1. **پاک‌سازی و تبدیل نوع داده‌ها (Type Coercion & Sanitization):** مقادیر متنی مانند فاصله‌های اضافی نام هتل یا حروف کوچک/بزرگ شهر به صورت خودکار `strip` می‌شوند و فرمت تاریخ‌ها یا اعداد منفی اعتبارسنجی می‌شوند.
2. **بررسی قیود میان‌فیلدی (Cross-Field Validation):** در متد `clean()` فرم `BookingQuoteForm`، بررسی می‌شود که تاریخ خروج بعد از تاریخ ورود باشد (`check_in < check_out`)، تاریخ ورود در گذشته نباشد، و تعداد مسافران از حداکثر ظرفیت اتاق تجاوز نکند.
3. **دیکشنری خطای استاندارد:** متد `form_errors(form)` خطاهای هر فیلد را به صورت آرایه‌ای از پیام‌های شفاف جهت نمایش زیر هر اینپوت به کلاینت ری‌اکت بازمی‌گرداند.

### Q3: چگونه مکانیزم تایید دو مرحله‌ای ایمیل بدون ذخیره توکن در دیتابیس کار می‌کند؟
**پاسخ:** از ماژول امنیتی `django.core.signing.TimestampSigner` استفاده شده است:
- هنگام ثبت‌نام، شناسه کاربر (`user.id`) و زمان فعلی با کلید محرمانه سامانه (`SECRET_KEY`) با الگوریتم HMAC-SHA256 امضا و Base64 می‌شوند و به عنوان پارامتر به لینک ایمیل ضمیمه می‌شوند.
- هنگامی که کاربر روی لینک کلیک می‌کند، متد `unsign(token, max_age=172800)` بررسی می‌کند که:
  ۱) آیا محتوای توکن دستکاری شده یا خیر (در صورت دستکاری امضا معتبر نبوده و خطای `BadSignature` می‌دهد).
  ۲) آیا بیش از ۴۸ ساعت از صدور گذشته است یا خیر (در صورت گذشت زمان خطای `SignatureExpired` می‌دهد).
- این معماری کاملاً **Stateless** است، ترافیک پایگاه داده ندارد، و نیازی به جدول موقت یا جاب‌های پاک‌سازی رکوردهای منقضی ندارد.

### Q4: تفاوت بین `Manager` و `QuerySet` در جنگو چیست و چرا در این پروژه از هر دو استفاده شده است؟
**پاسخ:**
- **`QuerySet`:** نماینده مجموعه‌ای از رکوردهای واکشی‌شده از دیتابیس است که قابلیت **زنجیره‌سازی متدها (Chaining)** را فراهم می‌کند. برای مثال می‌توان نوشت: `Hotel.objects.active().in_city("Isfahan").with_min_price()`. هر متد یک شیء `QuerySet` جدید بازمی‌گرداند.
- **`Manager`:** درگاه ورودی سطح بالای یک مدل است که به صورت پیش‌فرض از طریق `objects` در دسترس قرار می‌گیرد.
- **روش پیاده‌سازی ما:** برای جلوگیری از دوباره‌کاری (DRY)، با استفاده از کلاس `models.Manager.from_queryset(CustomQuerySet)`، منیجر پیش‌فرض مدل‌ها را مستقیماً از روی کوئری‌ست تولید کردیم. این روش تضمین می‌کند که تمامی متدهای زنجیره‌پذیر هم مستقیماً روی `Model.objects` و هم در زنجیره‌های بعدی کوئری در دسترس باشند.

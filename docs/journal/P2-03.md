## Why / design decisions (and alternatives rejected)
- **404 Not Found instead of 403 Forbidden for Foreign Objects**: In multi-tenant systems, returning 403 Forbidden when accessing an unowned object leaks information that an object with that ID exists in the database (ID enumeration attack). Returning 404 Not Found treats unowned objects as completely non-existent for the requesting manager, strictly fulfilling the DoD requirement.
- **ModelForm for Hotel and RoomType**: Django's `ModelForm` aligns directly with the course requirements (plain Django forms/views, no DRF). It cleanly handles model field validators (`MinValueValidator`, `MaxValueValidator`), unique constraints, and M2M relations while integrating seamlessly with our `form_errors(form)` helper.
- **M2M Amenities Handling**: `RoomTypeForm` leverages `forms.ModelMultipleChoiceField(queryset=Amenity.objects.all(), required=False)`. When receiving a JSON array of primary keys (e.g. `[1, 2]`), Django parses and validates their existence, and `form.save_m2m()` commits the relations to the through table.
- **Title Uniqueness per Hotel Validation**: While the database enforces `UniqueConstraint(fields=["hotel", "title"])`, catching duplicate room type titles in `RoomTypeForm.clean()` provides immediate, user-friendly field-level error messages (`{"errors": {"title": ["..."]}}`) rather than unhandled database integrity exceptions.
- **Preservation of `is_active` on Partial Updates**: In Django forms, boolean fields with missing keys can default to `False`. `HotelForm.clean_is_active()` checks if `is_active` was explicitly supplied in the request payload; if omitted during an update, it preserves `instance.is_active`.

## How it works (follow ONE request/click end to end)
1. **Manager Creates a Hotel**:
   - Client sends `POST /api/manager/hotels/` with session cookie, `X-CSRFToken`, and payload: `{"name": "Espinas Palace", "city": "Tehran", "address": "Saadat Abad", "star_rating": 5}`.
   - Request passes `@role_required("manager")` decorator verifying the user is logged in with `role == 'manager'`.
   - `parse_json(request)` extracts JSON body into a dictionary.
   - `HotelForm(data)` validates required fields and value ranges.
   - `form.save(commit=False)` initializes the model; `hotel.owner = request.user` binds ownership, then `hotel.save()` persists the record to PostgreSQL.
   - Endpoint returns HTTP 201 with `hotel_to_dict(hotel)`.
2. **Manager Creates Room Types with Amenities**:
   - Client sends `POST /api/manager/hotels/1/room-types/` with payload `{"title": "Royal Suite", "capacity": 3, "price_per_night": 4500000, "quantity": 4, "amenities": [1, 2]}`.
   - View queries `Hotel.objects.filter(id=1, owner=request.user).first()`.
   - If hotel belongs to another manager, view returns 404 immediately.
   - `RoomTypeForm` validates title uniqueness within hotel 1, checks that amenity IDs exist, and saves both the room type and its M2M amenities.
   - Endpoint returns HTTP 201 with `room_type_to_dict(room_type)`.

## Gotchas / things that surprised us
- In Django's `ModelMultipleChoiceField`, when data is passed as a Python list of integers from JSON (`[1, 2]`), `to_python` automatically queries the database and fetches model instances. If an invalid ID (e.g. `999`) is passed, Django cleanly populates `form.errors["amenities"]` without raising unhandled exceptions.
- In multi-tenant update endpoints, omitting a boolean field like `is_active` in a PUT request must be handled carefully so it does not accidentally flip an active hotel to inactive.

1. س: چرا در صورت درخواست یک مدیر برای مشاهده یا ویرایش هتل مدیری دیگر، به جای خطای ۴۰۳ (Permission Denied) خطای ۴۰۴ (Not Found) بازمی‌گردانید؟
   ج: این یک اصل امنیتی مهم در سیستم‌های چندمستأجره (Multi-Tenant) به نام جلوگیری از افشای شناسه (ID Enumeration / Object Existence Leakage) است. اگر پاسخ ۴۰۳ داده شود، مهاجم یا کاربر متخاصم متوجه می‌شود که رکوردی با این شناسه در سیستم وجود دارد اما مال او نیست. با بازگرداندن ۴۰۴، دیتابیس با شرط `owner=request.user` کوئری زده می‌شود و هیچ فرقی بین رکوردی که اصلاً وجود ندارد و رکوردی که متعلق به دیگری است گذاشته نمی‌شود؛ بنابراین وجود یا عدم وجود منابع دیگران کاملاً مخفی می‌ماند.
2. س: روابط چندبه‌چند (M2M) امکانات اتاق (`amenities`) در فرم و ذخیره‌سازی چگونه مدیریت شدند؟
   ج: از فیلد استاندارد `forms.ModelMultipleChoiceField(queryset=Amenity.objects.all(), required=False)` در `RoomTypeForm` استفاده شد. کلاینت لیست شناسه‌های امکانات را به صورت آرایه جی‌سان (`[1, 2]`) ارسال می‌کند. فرم جنگو به طور خودکار معتبر بودن شناسه‌ها را بررسی می‌کند. در متد `save` فرم، با فراخوانی متد `self.save_m2m()` پس از ذخیره شیء `RoomType`، رکوردهای جدول واسط (`hotels_roomtype_amenities`) در دیتابیس درج و به‌روزرسانی می‌شوند.
3. س: چگونه از تکراری شدن عنوان نوع اتاق در یک هتل جلوگیری می‌کنید بدون اینکه استثنای خطای ۵۰۰ تولید شود؟
   ج: اگرچه در مدل `RoomType` قید یکتایی `UniqueConstraint(fields=["hotel", "title"])` روی دیتابیس وجود دارد، اما اگر ولیدیشن در فرم انجام نشود پایگاه داده خطای `IntegrityError` داده و سرور خطای ۵۰۰ بازمی‌گرداند. برای جلوگیری از این اتفاق، در متد `clean` فرم `RoomTypeForm`، کوئری `RoomType.objects.filter(hotel=self.hotel, title__iexact=title)` اجرا می‌شود (و در صورت ویرایش، رکورد فعلی استثنا می‌گردد). در صورت وجود عنوان تکراری، با `self.add_error("title", "...")` خطای ولیدیشن ۴۰۰ به کلاینت بازگردانده می‌شود.
4. س: کنترل دسترسی نقش مدیر هتل در این تسک چگونه پیاده‌سازی شده است؟
   ج: تمام ویوهای منیجر با دکوراتور سفارشی `@role_required("manager")` که در P2-01 پیاده شده محافظت شده‌اند. این دکوراتور ابتدا احراز هویت کاربر را بررسی می‌کند (در صورت لاگین نبودن پاسخ ۴۰۱ جی‌سان)، سپس بررسی می‌کند که آیا نقش کاربر در مدل `User` برابر `manager` است یا خیر؛ در صورتی که کاربر مهمان (guest) باشد پاسخ ۴۰۳ جی‌سان بازمی‌گرداند. در نهایت درون خود ویو نیز فیلترهای مالکیتی روی `owner=request.user` اجرا می‌شوند.
5. س: برای اندپوینت‌های ویرایش (PUT) چگونه مطمئن شدید مقادیری مثل `is_active` در صورت ارسال نشدن ناخواسته مقدار `False` نمی‌گیرند؟
   ج: در فرم‌های استاندارد جنگو، فیلدهای `BooleanField` در صورتی که در دیکشنری ورودی وجود نداشته باشند به صورت پیش‌فرض مقدار `False` برمی‌گردانند (رفتاری که از چک‌باکس‌های HTML نشأت می‌گیرد). برای جلوگیری از این مشکل در API، در متد `clean_is_active` فرم `HotelForm` بررسی کردیم که اگر کلید `is_active` در `self.data` وجود نداشت، مقدار فیلد از نمونه موجود (`self.instance.is_active`) حفظ شود و در صورت ساخت جدید، مقدار پیش‌فرض `True` قرار گیرد.

## Why / design decisions (and alternatives rejected)
- **Centralized Hotel State Synchronization**: Rather than having each tab independently query the manager's hotels list, `ManagerPage` orchestrates the selected hotel and shares the live list with child tabs. When a manager adds or deletes a hotel in `HotelListTab`, `onHotelsChange` propagates the updated list across tabs, preventing stale select dropdowns.
- **URL Query Parameter State Persistence (`?tab=...&hotelId=...`)**: Managing active tab and current hotel in URL search params ensures that browser refresh (`F5`), back/forward navigation, or deep links retain the exact sub-tab and hotel context.
- **Client & Server Validation Error Separation**: Modals display immediate client-side required field validations while catching `ApiError` instances from Django views to render server-side field-level errors (e.g. unique constraints or invalid dates) directly underneath the corresponding input fields.
- **Color-Coded Capacity Heatmap**: For the availability tab, showing raw numbers alone can be hard to scan. Introducing color indicators (emerald for plenty, amber for low stock <= 2, rose for zero free) allows managers to instantly identify high-demand and fully booked days.
- **Strict Role Guarding**: Manager page is guarded by `<RequireRole role="manager">` at the router level in `frontend/src/App.jsx`, ensuring unauthorized guests receive an explicit 403 screen without exposing manager data or endpoints.

## How it works (follow ONE request/click end to end)
1. **Manager registers or logs in**: User with `role: "manager"` logs in; `Navbar` displays the "پنل مدیریت" navigation item.
2. **Accessing Manager Dashboard**: Clicking "پنل مدیریت" navigates to `/manager`. `RequireRole` validates role `manager`.
3. **Viewing and Creating Hotel**:
   - `HotelListTab` executes `getManagerHotelsApi()` (`GET /api/manager/hotels/`), receiving the authenticated manager's hotels.
   - User clicks "افزودن هتل جدید", fills name, city, address, star rating, and clicks submit.
   - `createManagerHotelApi()` sends `POST /api/manager/hotels/` with CSRF token.
   - The new hotel appears in the cards grid, and `ManagerPage` updates its selected hotel state.
4. **Defining Room Types with Amenities**:
   - User clicks "🚪 اتاق‌ها" on the hotel card; URL updates to `/manager?tab=rooms&hotelId=X`.
   - `RoomTypeModal` fetches amenities from `GET /api/amenities/` and displays checkboxes (WiFi, Pool, Breakfast...).
   - User inputs title, capacity (2), price (1,500,000), quantity (5), selects amenities, and submits.
   - `createManagerRoomTypeApi()` posts data to `/api/manager/hotels/X/room-types/`.
5. **Checking Daily Availability**:
   - User clicks "📊 تقویم ظرفیت"; URL updates to `/manager?tab=availability&hotelId=X`.
   - `getManagerAvailabilityApi()` requests `GET /api/manager/hotels/X/availability/?date_from=...&date_to=...`.
   - Server returns daily breakdown; table renders each date with total rooms, booked count, and remaining free count in green/amber/rose cells.
6. **Creating Discount Code**:
   - User switches to "کدهای تخفیف", enters code `SUMMER20`, 20% discount, selects validity dates, and saves.
   - `createManagerDiscountApi()` sends `POST /api/manager/hotels/X/discounts/`.

## Gotchas / things that surprised us
- **Date Timezone Shift in JavaScript**: When converting date strings like `YYYY-MM-DD` with `new Date("2026-11-07")`, JavaScript parses them as UTC midnight. Depending on the local client timezone offset, calling `.toLocaleDateString()` could shift the day backward to the previous day. Appending midday time (`${dt}T12:00:00`) completely eliminates any timezone boundary shift.
- **State Synchronization on Hotel Addition**: If each manager sub-tab maintains its own list of hotels or only relies on initial mount state, creating a hotel in the "Hotels" tab would leave the dropdowns in other tabs unaware of the new hotel until page reload. Providing an `onHotelsChange` callback keeps the parent and all tabs instantly synchronized.

2. **س: چرا در ارسال فرم‌های ویرایش و ثبت اطلاعات مدیر (مثل هتل، نوع اتاق و تخفیف) به هدر CSRF نیاز است و چطور تامین می‌شود؟**
   - **ج:** بر اساس تصمیم معماری پروژه (D-003)، احراز هویت از طریق کوکی نشست جنگو (Session Auth) صورت می‌گیرد و از توکن‌های ناامن در `localStorage` استفاده نمی‌شود. بنابراین تمام متدهای جهش‌دهنده داده (`POST`, `PUT`, `DELETE`) مشمول محافظت جنگو در برابر جعل درخواست میان‌سایتی (CSRF) هستند. ماژول `client.js` با بررسی خودکار کوکی و فراخوانی اندپوینت `ensureCsrfToken()` هدر `X-CSRFToken` را در تمام درخواست‌های جهش تزریق می‌کند.

3. **س: ارتباط بین تب‌های صفحه مدیر و اشتراک‌گذاری داده‌ها (مانند هتل انتخاب‌شده) چگونه پیاده‌سازی شده است؟**
   - **ج:** مدیریت وضعیت به صورت متمرکز در کامپوننت `ManagerPage` انجام می‌شود و وضعیت تب فعال (`tab`) و هتل انتخاب‌شده (`hotelId`) با `useSearchParams` در URL همگام می‌گردد. این کار سه مزیت دارد: امکان بوک‌مارک و اشتراک‌گذاری لینک، حفظ تب فعال در هنگام رفرش صفحه (`F5`)، و همگام‌سازی بلافاصله هتل انتخاب‌شده در هنگام جابجایی بین تب‌های اتاق‌ها، رزروها و تقویم ظرفیت.

4. **س: تقویم موجودی روزانه هتل (Availability) چه اطلاعاتی را نشان می‌دهد و چطور محاسبه می‌شود؟**
   - **ج:** این بخش با ارسال شناسه هتل و بازه تاریخی `date_from` و `date_to` به اندپوینت `/api/manager/hotels/{id}/availability/` داده‌های هر روز را دریافت می‌کند. سرور تعداد کل اتاق‌های فیزیکی، تعداد اتاق‌های رزرو شده فعال و ظرفیت آزاد (`free = total - reserved`) را برمی‌گرداند. در فرانت‌اند با یک جدول ماتریسی، هر روز در ستون و نوع اتاق در ردیف قرار گرفته و با رنگ‌های متمایز (سبز برای ظرفیت مناسب، زرد برای ظرفیت کمتر از ۲ و قرمز برای ظرفیت تکمیل) نمایش داده می‌شود.

5. **س: نحوه نمایش خطاهای اعتبارسنجی ارسالی از سمت سرور به چه شکل است؟**
   - **ج:** ویوهای فرم در جنگو خطاها را در ساختار استانداردی بازمی‌گردانند (`{"message": "...", "errors": {"field_name": ["error_message"]}}`). در مدال‌های فرانت‌اند، خطاهای کلاس `ApiError` رهگیری شده و مستقیماً زیر فیلد مربوطه (مثلاً خطای تکراری بودن عنوان نوع اتاق یا کد تخفیف در همان هتل) با رنگ قرمز رندر می‌شوند تا مدیر سریعاً فیلد نامعتبر را اصلاح کند.

## Why / design decisions (and alternatives rejected)
- **Django Session Auth over localStorage tokens (D-003)**: In adherence to the course requirements, authentication is entirely handled via secure HTTP-only session cookies and CSRF protection. No JWT tokens or credentials are stored in `localStorage` or `sessionStorage`, mitigating XSS credential theft.
- **Automatic CSRF Token Seeding in `client.js`**: When a first-time visitor attempts an authentication mutation (`/api/auth/login/` or `/api/auth/register/`), no CSRF cookie might exist yet in the browser. The enhanced `apiRequest` detects mutating methods and automatically fetches `/api/auth/csrf/` if `csrftoken` is absent before proceeding, completely eliminating CSRF verification failures.
- **Targeted Field-Level Error Binding**: Rather than generic toast alerts, errors returned by Django's `form_errors` envelope are mapped directly to individual form inputs (e.g., `errors.username`, `errors.password`), providing immediate feedback inline.
- **Loading Gating in Route Guards**: `RequireAuth` and `RequireRole` render a spinner while `AuthContext` is checking initial user state from `/api/auth/me/`, avoiding flash-of-unauthenticated-content or premature redirects on page refresh.

## How it works (follow ONE request/click end to end)
1. **User Registration & Auto-Login**:
   - Guest visits `/register`, fills in `username`, `email`, `password`, `password2`, selects role `guest`, and submits.
   - `client.js` ensures `csrftoken` exists, then posts data to `/api/auth/register/`.
   - On success (201), `AuthContext.register()` immediately calls `login()` with the newly created credentials.
   - User state is set in context, and user is navigated to `/` with the greeting "سلام، [username]" in the navbar.
2. **Session Persistence on Refresh**:
   - User presses `F5` / browser refresh.
   - `AuthContext` mounts with `loading = true` and sends `GET /api/auth/me/`.
   - Django session cookie validates user, returning `{"data": {"id": 1, "username": "...", "role": "guest", ...}}`.
   - `AuthContext` sets `user` and `loading = false`; session is seamlessly restored without re-login.
3. **Role Protection for `/manager`**:
   - A logged-in guest user enters `/manager` directly into the browser URL bar.
   - `RequireRole` detects `user.role === 'guest' !== 'manager'`.
   - Access is denied and a 403 screen is rendered ("دسترسی غیرمجاز. این قسمت مخصوص مدیران هتل می‌باشد.") preventing access to the manager panel.
4. **Logout**:
   - User clicks "خروج" in the navbar.
   - `logoutApi()` sends `POST /api/auth/logout/` with CSRF token.
   - Server flushes session; `AuthContext` clears `user` state and navigates user to `/login`.

## Gotchas / things that surprised us
- In React Fast Refresh with ESLint, exporting both a component (`AuthProvider`) and a hook (`useAuth`) in the same file triggered `react-refresh/only-export-components`. Adding a targeted eslint disable directive resolved the warning while keeping the context and hook cleanly colocated.
- During registration, Django's `RegisterForm` creates the user but does not automatically issue a session cookie. Chaining an automatic `loginApi` call within `register()` provides a modern SPA experience where the user is immediately logged in upon successful sign-up.

2. **س: چرا برای ارسال درخواست‌های تغییردهنده (POST/PUT/DELETE) به توکن CSRF نیاز است و فرانت‌اند آن را چگونه مدیریت می‌کند؟**
   **ج:** برای جلوگیری از حملات جعل درخواست بین سایتی (CSRF)، جنگو نیازمند هدر `X-CSRFToken` در تمام متدهای تغییردهنده حالت است. در فایل `client.js` تابعی به نام `ensureCsrfToken` تعبیه شده که قبل از ارسال هر درخواست `POST/PUT/PATCH/DELETE`، وجود کوکی `csrftoken` را در مرورگر چک می‌کند؛ در صورتی که این کوکی وجود نداشته باشد، ابتدا یک درخواست سبک به اندپوینت `/api/auth/csrf/` می‌زند تا کوکی در مرورگر ست شود و سپس مقدار آن را در هدر `X-CSRFToken` قرار می‌دهد.

3. **س: خطاهای اعتبارسنجی سرور (Field Errors) چگونه از بک‌اند دریافت و در فرم‌های ورود و ثبت‌نام نمایش داده می‌شوند؟**
   **ج:** در بک‌اند جنگو، کلاس `form_errors` خطاها را به صورت یک آبجکت شامل نام فیلد و آرایه پیام‌های خطا (مانند `{"username": ["This username is taken."]}`) بازمی‌گرداند. فرانت‌اند در کلاس `ApiError` این خطاها را نگهداری کرده و در فرم‌های `LoginPage` و `RegisterPage` این فیلدها را در آبجکت `fieldErrors` ذخیره می‌کند. در نتیجه هر خطا دقیقاً در زیر فیلد مربوط به خودش با رنگ قرمز نمایش داده می‌شود و خطاهای کلی در بنر بالای فرم نشان داده می‌شوند.

4. **س: مکانیزم محافظت از مسیرها (Route Guards) چگونه از دسترسی کاربران غیرمجاز یا مهمان به بخش مدیریت جلوگیری می‌کند؟**

   **ج:** طبق الزامات پروژه و تصمیم معماری D-003، استفاده از توکن‌های JWT و ذخیره توکن احراز هویت در `localStorage` به دلیل آسیب‌پذیری در برابر حملات تزریق اسکریپت (XSS) ممنوع است. در معماری Session Cookie جنگو، کلید سشن در یک کوکی با پرچم‌های امنیتی نگهداری می‌شود و وضعیت واقعی ورود در سمت سرور کنترل می‌گردد که امکان ابطال آنی نشست هنگام خروج (`logout`) را به سرور می‌دهد.

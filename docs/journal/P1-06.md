## Why / design decisions (and alternatives rejected)
- **Early Bonus-Ready Schema**: Defining `Review` in Phase 1 ensures the database schema remains stable. When implementing reviews & ratings in Phase 4 (P4-12), no disruptive schema migrations or altering of existing relationships will be required.
- **Composite Unique Constraint `(hotel, user)`**: A guest should have at most one rating/review per hotel establishment. If they want to revise their feedback, they can edit the existing review.
- **Defense in Depth for Rating Bounds**: Combining Python validators with PostgreSQL `CheckConstraint` ensures clean validation messages in Django forms and admin while guaranteeing that direct ORM or raw query operations cannot violate the 1–5 star invariant.
- **FK Deletion Policies (`CASCADE`)**: Unlike `Booking` (where financial audit trails necessitate `PROTECT`), reviews are dependent user-generated content. Deleting a hotel or user should cleanly cascade and delete associated reviews without leaving orphaned records.
- **Deterministic Ordering `["-created_at", "-id"]`**: Relying solely on `created_at` can lead to unstable sorting when rows share identical microsecond timestamps (especially on Windows or fast test runs). Adding `-id` guarantees deterministic ordering for pagination.

## How it works (follow ONE request/click end to end)
1. A guest submits a review for a hotel with a 1–5 star rating and an optional comment.
2. The model validates that `1 <= rating <= 5`.
3. When saving to PostgreSQL:
   - The engine validates that `rating >= 1 AND rating <= 5` via `CheckConstraint`.
   - The engine checks that no existing review exists for the same `(hotel_id, user_id)` pair via `UniqueConstraint`.
4. If valid, the review is saved and immediately accessible via `hotel.reviews.all()` and `user.reviews.all()`.

  ```python
  from apps.hotels.models import Hotel
  from apps.reviews.models import Review
  from django.contrib.auth import get_user_model
  User = get_user_model()

  g = User.objects.filter(role=User.Role.GUEST).first()
  h = Hotel.objects.first()

  # Test 1: Valid review
  r = Review.objects.create(hotel=h, user=g, rating=5, comment="Great stay!")
  print("Review created:", r)

  # Test 2: UniqueConstraint violation
  try:
      with transaction.atomic():
          Review.objects.create(hotel=h, user=g, rating=3)
  except IntegrityError as e:
      print("Caught expected duplicate review IntegrityError:", str(e).strip().splitlines()[0])

  # Test 3: CheckConstraint violation (rating > 5)
  try:
      with transaction.atomic():
          Review.objects.create(hotel=h, user=User.objects.last(), rating=10)
  except IntegrityError as e:
      print("Caught expected rating range IntegrityError:", str(e).strip().splitlines()[0])
  ```

## Gotchas / things that surprised us
- In tests creating multiple objects within sub-millisecond intervals on Windows, two records can receive identical timestamps under `auto_now_add=True`. Adding `-id` to `ordering` and explicitly separating timestamps in tests ensures rock-solid, deterministic test assertions and pagination.

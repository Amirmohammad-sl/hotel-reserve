## Why / design decisions (and alternatives rejected)
- **Eliminating magic strings & centralising role logic**: Without `User.objects.managers()` and `.guests()`, views and permissions repeat `filter(role="manager")` and `filter(role="guest")`. Centralising query logic in `UserQuerySet` keeps code DRY and avoids typo-prone strings.
- **SQL MIN aggregation vs N+1 loops**: When listing hotels, search cards display "Starting from X Toman". Calculating this by looping through `hotel.room_types.all()` in Python produces an N+1 query problem. `.with_min_price()` executes SQL `MIN("hotels_roomtype"."price_per_night")` in a single query directly in the database engine.
- **Single-filter multi-valued relationship resolution**: In Django ORM, filtering a reverse ForeignKey in chained `.filter()` calls (`.filter(room_types__price_per_night__gte=min).filter(room_types__price_per_night__lte=max)`) joins the `room_types` table twice, which can erroneously match a hotel where room A satisfies `gte` and room B satisfies `lte` even if no single room is in range. In `priced_between()`, both bounds are passed to a single `.filter(**filters)` call to ensure they target the exact same room type record.
- **Robust city query normalization**: Search inputs from end users frequently contain leading/trailing spaces or mixed Persian/English casing. `.in_city(city)` performs `.strip()` and uses `city__iexact` to guarantee clean matching.
- **Tenant security scoping**: `.owned_by(user)` provides a unified domain boundary for manager dashboards, preventing horizontal privilege escalation without duplicating `owner=request.user` across manager views.

## How it works (follow ONE request/click end to end)
1. **Public hotel search with starting price & budget filtering**:
   - A guest searches for active hotels in Tehran with nightly price between 1,000,000 and 3,000,000 Toman.
   - The view executes:
     ```python
     Hotel.objects.active().in_city("tehran").with_min_price().priced_between(1_000_000, 3_000_000)
     ```
   - Django executes a single optimized SQL query:
     ```sql
     SELECT DISTINCT "hotels_hotel".*,
            MIN("hotels_roomtype"."price_per_night") AS "min_price"
     FROM "hotels_hotel"
     LEFT OUTER JOIN "hotels_roomtype"
       ON ("hotels_hotel"."id" = "hotels_roomtype"."hotel_id")
     WHERE ("hotels_hotel"."is_active" = TRUE
       AND UPPER("hotels_hotel"."city"::text) = UPPER('tehran')
       AND "hotels_roomtype"."price_per_night" >= 1000000
       AND "hotels_roomtype"."price_per_night" <= 3000000)
     GROUP BY "hotels_hotel"."id";
     ```
   - Each returned hotel object immediately has `.min_price` populated with zero extra queries.

2. **Manager dashboard isolation**:
   - A hotel manager logs into the dashboard to view their establishments.
   - The view simply calls `Hotel.objects.owned_by(request.user)`.
   - The query guarantees that manager A cannot view, edit, or manipulate manager B's hotels.

## Gotchas / things that surprised us
- **Spanning Multi-Valued Relationships in Django ORM**: If `priced_between` used two separate `.filter(room_types__price_per_night__gte=min).filter(room_types__price_per_night__lte=max)`, Django would create two separate `JOIN` operations on the room types table. This would cause hotels with rooms at 50,000 and 500,000 to falsely match a range of `[100,000, 300,000]`! Grouping the filters in a single `.filter(**filters)` call ensures both criteria apply to the exact same room type instance.
- **Manager inheritance via `from_queryset`**: Defining `UserManager(DefaultUserManager.from_queryset(UserQuerySet))` ensures that methods like `.managers()` and `.guests()` are available both directly on `User.objects` and on any chained queryset (e.g. `User.objects.filter(is_active=True).managers()`).

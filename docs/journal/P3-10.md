## Why / design decisions (and alternatives rejected)
- **Layered Logging (Domain Services vs HTTP Views)**:
  - *Alternative rejected*: Logging only at HTTP view layer or only at domain service layer.
  - *Chosen approach*: Domain business logic (e.g. why a discount was invalid, room stock exhaustion under row lock, restored discount usage count) is logged directly inside `services.py` with full entity context. The HTTP view layer records request-level lifecycle events (form parsing failures, HTTP status codes emitted, user identification). This separation ensures that even if background workers or shell commands invoke `services.py` directly, domain events remain fully audible.
- **Auditing Security Breaches via `apps.security`**:
  - Unauthorised attempts to cancel someone else's reservation or probing non-existent reservation IDs are routed directly to `apps.security` (which outputs to `logs/security.log`), matching the security auditing established in P3-08 and P3-09.
- **Semantic Logging Levels**:
  - `DEBUG`: High-frequency read queries and intermediate calculations (`BookingQuerySet.overlapping`, quote calculations, listing user's bookings). These provide granular tracing during local debugging without polluting production logs.
  - `INFO`: Significant state mutations and business lifecycle transitions (confirmed booking created, reservation cancelled, valid coupon verified).
  - `WARNING`: Recoverable business conflicts or rejected inputs (concurrency conflict 409, invalid check-in/out dates, form errors, unauthorized cancellations).
- **Evaluating Querysets Efficiently When Logging Collections**:
  - In `my_bookings_list_view`, converting `bookings` to `list(bookings)` once evaluates the database queryset, allowing both `len(bookings_list)` for diagnostic logging and serialization to JSON without issuing a duplicate `COUNT(*)` query.
- **Zero Sensitive Data Invariant (Hard Rule 9)**:
  - No payment card data, passwords, session tokens, or sensitive guest credentials appear in any log statements. All identifiers are logged purely by primary key (`booking_id`, `guest_id`, `room_type_id`, `hotel_id`) and normalized coupon codes.

## How it works (follow ONE request/click end to end)
1. **Guest Books Last Available Room via `POST /api/bookings/`:**
   - A guest sends a booking request with `room_type=5`, dates `2026-11-20` to `2026-11-22`, and coupon `AUTUMN20`.
   - `RequestLogMiddleware` captures the incoming request and starts the timer.
   - `booking_create_view` parses JSON and validates `BookingQuoteForm`.
   - Control delegates to `create_booking` in `services.py`.
   - Inside `transaction.atomic()`, `select_for_update()` locks `RoomType` and `DiscountCode`.
   - `validate_discount_code` checks validity and logs:
     `2026-11-08 21:56:10 [INFO] [apps.bookings.services] Discount code applied: code='AUTUMN20' hotel_id=12 discount_id=4 percent=20`
   - `calculate_booking_quote` computes quote and logs:
     `2026-11-08 21:56:10 [DEBUG] [apps.bookings.services] Quote calculated: room_type_id=5 check_in=2026-11-20 check_out=2026-11-22 rooms=1 nights=2 subtotal=6000000 discount=1200000 total=4800000 available=True`
   - `Booking.objects.create(...)` records the reservation, and `DiscountCode.used_count` is incremented.
   - `create_booking` emits:
     `2026-11-08 21:56:10 [INFO] [apps.bookings.services] Booking created: booking_id=105 guest_id=14 room_type_id=5 hotel_id=12 check_in=2026-11-20 check_out=2026-11-22 rooms=1 total_price=4800000 discount_id=4`
   - `booking_create_view` logs confirmation:
     `2026-11-08 21:56:10 [INFO] [apps.bookings.views] Booking created successfully: booking_id=105 guest_id=14 room_type_id=5 total_price=4800000`
   - Response returns HTTP 201 Created. `RequestLogMiddleware` logs completion:
     `2026-11-08 21:56:10 [INFO] [apps.core.middleware] POST /api/bookings/ 201 user_id=14 duration_ms=28.45`

2. **Simultaneous Second Guest Attempts to Book Same Room (Conflict):**
   - Second guest's request waits on the row lock, then evaluates availability upon lock release.
   - `available_count` evaluates to 0. `create_booking` logs:
     `2026-11-08 21:56:10 [WARNING] [apps.bookings.services] Booking conflict: requested 1 room(s) unavailable for room_type_id=5 hotel_id=12 check_in=2026-11-20 check_out=2026-11-22 available=0 guest_id=15`
   - `AvailabilityConflictError` is raised. View catches it and logs:
     `2026-11-08 21:56:10 [WARNING] [apps.bookings.views] Booking create conflict for user_id=15 room_type_id=5: Requested 1 room(s) not available for the selected dates (only 0 available).`
   - HTTP 409 Conflict is returned safely without data corruption or double booking.

## Gotchas / things that surprised us
- In Django's test runner, tests using `assertLogs` intercept logs only at or above the specified level for the named logger hierarchy. For compound operations where both `apps.bookings.services` and `apps.bookings.views` log simultaneously, nesting `with self.assertLogs(...)` context managers allows verifying emissions from both domain and view layers cleanly without mutual interference.
- When logging the length of query results in `my_bookings_list_view`, calling `len(bookings)` directly on a lazy queryset forces a separate SQL query or un-cached evaluation. By casting the queryset to `bookings_list = list(bookings)` first, the rows are fetched into memory once and reused immediately for both logging the count and building the serialized JSON dictionary list.

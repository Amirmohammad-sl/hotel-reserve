## Why / design decisions (and alternatives rejected)
- **Database constraints at ORM level**: Defining `CheckConstraint` in PostgreSQL guarantees data consistency regardless of whether reservations are created via web views, shell commands, or batch tasks.
- **FK Deletion Policies**:
  - `guest` and `room_type` use `on_delete=models.PROTECT` because reservations represent audit/financial history and must never be silently cascaded on user or room deletion.
  - `discount_code` uses `on_delete=models.SET_NULL` with snapshots of `price_per_night_snapshot`, `subtotal`, and `discount_amount` on the booking, ensuring historical records remain intact even if a coupon code is later deleted.
- **Pure function for `calculate_nights()`**: Kept free of database access or side effects to ensure fast, deterministic calculations usable anywhere in forms, views, or business logic.
- **Composite Index for Availability**: Overlap logic (decision D-006) evaluates `existing.check_in < new.check_out AND existing.check_out > new.check_in` for a specific `room_type`. The compound index `(room_type, check_in, check_out)` allows PostgreSQL to perform an efficient index scan.

## How it works (follow ONE request/click end to end)
1. A guest initiates a reservation for a selected room type.
2. The system checks `check_in` and `check_out` dates and calculates stay duration using `booking.calculate_nights()`.
3. Total price is computed using `price_per_night_snapshot` and optional `DiscountCode`.
4. When saving the `Booking`, PostgreSQL validates constraints:
   - `check_out > check_in`
   - `rooms_count >= 1` and `guests_count >= 1`
   - `nights >= 1`
5. If valid, the reservation is committed to the database with status `confirmed`, indexed for immediate availability checks.

## Gotchas / things that surprised us
- In Django unit tests using PostgreSQL inside atomic blocks, raising a database-level `IntegrityError` aborts the transaction at PostgreSQL level. Any subsequent queries within that test method will fail with `TransactionManagementError` unless the failing query is wrapped in `with transaction.atomic():`, creating a savepoint that rolls back cleanly.

## Viva Q&A (Persian, 3–5) — questions the professor could ask about this task
1. س: چرا برای فیلد check_out قید check_out > check_in را در سطح دیتابیس (CheckConstraint) گذاشتید و فقط به متد clean در مدل یا فرم اکتفا نکردید؟
   ج: متد clean یا فرم‌ها فقط در لایه پایتون و هنگام فراخوانی صریح فرم‌ها اجرا می‌شوند. اگر رکوردی از طریق اسکریپت‌ها، API بدون اعتبارسنجی فرم، یا متدهای دیگر ایجاد شود، اعتبارسنجی پایتونی دور زده می‌شود. با تعریف `CheckConstraint` در پایگاه داده PostgreSQL، تحت هیچ شرایطی رکوردی با تاریخ خروج نامعتبر وارد دیتابیس نمی‌شود.
2. س: چرا ارتباط guest و room_type با مدل Booking به صورت on_delete=models.PROTECT تعریف شده است؟
   ج: رکوردهای رزرو اسناد مالی و تاریخچه‌ای مهم سیستم هستند. اگر هتلی یا کاربری حذف شود و رابطه CASCADE باشد، تمام سوابق رزرو و مالی پاک خواهند شد که یک خطای بزرگ تجاری و حسابداری است. با PROTECT از حذف ناخواسته اتاق یا کاربری که سابقه رزرو دارد در سطح دیتابیس جلوگیری می‌شود.
3. س: چرا متد calculate_nights() باید یک تابع خالص (pure function) باشد و چرا تعداد شب‌ها (nights) به صورت فیلد فیزیکی در جدول رزرو ذخیره می‌شود؟
   ج: تابع خالص ورودی‌هایش را از مشخصه‌های شیء (`check_in` و `check_out`) می‌گیرد و هیچ کوئری به دیتابیس نمی‌زند، بنابراین بسیار سریع و بدون اثر جانبی است. ذخیره مقدار `nights` به صورت ستون در دیتابیس طبق تصمیم معماری D-004، امکان گزارش‌گیری سریع، اعمال قیود پایگاه‌داده و کوئری‌زدن روی مدت اقامت بدون نیاز به محاسبه تفاضل تاریخ در هر کوئری SQL را فراهم می‌کند.
4. س: نقش ایندکس ترکیبی (room_type, check_in, check_out) در مدل Booking چیست؟
   ج: طبق تصمیم D-006، الگوریتم بررسی اتاق‌های خالی (`availability`) نیازمند بررسی همپوشانی بازه‌های زمانی رزروها روی یک نوع اتاق خاص است (`existing.check_in < new.check_out AND existing.check_out > new.check_in`). ایندکس ترکیبی سه‌ستونی باعث می‌شود کوئری جستجوی همپوشانی مستقیماً از Index Scan به جای اسکن کل جدول (Full Table Scan) استفاده کرده و با سرعت بسیار بالا اجرا شود.

## Why / design decisions (and alternatives rejected)
- **HTTP 409 Conflict for overbooking**: In full accordance with `API_CONTRACT.md` and REST best practices, when inventory is insufficient for the requested dates, the endpoint responds with HTTP 409 Conflict instead of generic 400 Bad Request.
- **Transactional atomicity (`transaction.atomic`)**: Booking creation and cancellation modify both `Booking` and `DiscountCode` records. Wrapping these operations inside database transactions ensures no inconsistent intermediate states occur.
- **Availability based on `confirmed` status (D-006)**: Since `calculate_room_type_available_count` checks only bookings with `status == Booking.Status.CONFIRMED`, marking a booking as `cancelled` immediately frees up inventory without needing complex room reassignment.
- **Snapshotting prices and discount details**: Room prices and discount percentages may change in the future. Snapshotting `price_per_night_snapshot`, `subtotal`, `discount_amount`, and `total_price` on the `Booking` record preserves financial auditability even if discount codes or room types are later modified or soft-deleted.

## How it works (follow ONE request/click end to end)
1. **Quote Request**:
   - Guest sends `POST /api/bookings/quote/` with room type, check-in, check-out, room count, and optional discount code.
   - `quote_view` validates input via `BookingQuoteForm` and invokes `calculate_booking_quote`.
   - Response returns `{nights, subtotal, discount_amount, total_price, available}`.
2. **Booking Creation**:
   - Guest sends `POST /api/bookings/` with the same payload.
   - `booking_create_view` runs `create_booking`.
   - If rooms are available:
     - Discount `used_count` increments by 1.
     - Booking is saved with status `confirmed`.
     - Returns HTTP 201 with serialized booking.
   - If room inventory is exhausted:
     - Returns HTTP 409 Conflict `{"message": "Requested ... room(s) not available for the selected dates..."}`.
3. **Booking Cancellation**:
   - Guest sends `POST /api/bookings/{id}/cancel/`.
   - `booking_cancel_view` validates that booking belongs to guest, is currently `confirmed`, and check-in date is in the future.
   - Sets status to `cancelled`, records `cancelled_at`, and decrements discount `used_count` by 1.
   - Rooms become immediately available for other guests.

## Gotchas / things that surprised us
- In Python 3.15 test environment, Django's admin changelist test hits a template context copying incompatibility (`BaseContext.__copy__`). Adding the lightweight context copying patch introduced in P2-05 ensures local testing under 3.15 passes cleanly without altering behavior under 3.12 in CI.
- For cancellation, checking `check_in > timezone.localdate()` strictly prevents guests from cancelling a booking on the day of arrival or after departure, ensuring compliance with hotel cancellation policies.

## Viva Q&A (Persian, 3–5) — questions the professor could ask about this task
1. **س: چرا در صورت پر بودن ظرفیت اتاق‌ها به جای خطای ۴۰۰ (Bad Request) از خطای ۴۰۹ (Conflict) استفاده کردید؟**
   **ج:** کد وضعیت HTTP 400 نشان‌دهنده خطای کلاینت در ارسال داده‌های نامعتبر فرمت یا ساختار ورودی است؛ در حالی که درخواست رزرو از نظر قواعد فرمت و نوع داده کاملاً معتبر است اما به دلیل تعارض با وضعیت جاری منابع سرور (پر بودن ظرفیت فیزیکی اتاق در تاریخ‌های درخواستی) امکان پردازش آن وجود ندارد. طبق استاندارد RFC 9110 و قرارداد صریح پروژه (`docs/API_CONTRACT.md`)، کد وضعیت مناسب برای تعارض بر سر منابع موجود HTTP 409 Conflict است.

2. **س: مکانیزم لغو رزرو چگونه اتاق‌ها را مجدداً آزاد می‌کند؟ آیا نیازی به تغییر جدول خاصی است؟**
   **ج:** بر اساس تصمیم معماری D-006، ظرفیت خالی اتاق‌ها (`availability`) به صورت پویا از کسر رزروهای با وضعیت `confirmed` در بازه تاریخی اقامت از کل تعداد فیزیکی اتاق‌ها محاسبه می‌شود. بنابراین با فراخوانی متد لغو، وضعیت رزرو به `cancelled` تغییر کرده و فیلد زمان لغو `cancelled_at` ثبت می‌شود. از آنجا که کوئری محاسبه ظرفیت، رزروهای `cancelled` را نادیده می‌گیرد، اتاق‌ها به صورت آنی و خودکار برای سایر کاربران آزاد می‌شوند.

3. **س: چرا شمارنده استفاده از کد تخفیف (`used_count`) و ساخت رزرو باید درون یک تراکنش اتمیک (`transaction.atomic`) قرار گیرند؟**
   **ج:** اگر ساخت رزرو و افزایش شمارنده کد تخفیف به صورت مجزا انجام شوند، در صورتی که ساخت رزرو به هر دلیلی (مثل خطای شبکه یا نقض قید دیتابیس) شکست بخورد، شمارنده کد تخفیف ممکن است افزایش یافته باقی بماند یا برعکس. استفاده از بلوک `transaction.atomic()` تضمین می‌کند که یا هر دو عمل (ثبت رکورد رزرو و به‌روزرسانی کد تخفیف) با موفقیت در پایگاه داده Commit می‌شوند و یا در صورت بروز هرگونه استثنا، کل عملیات Rollback شده و وضعیت دیتابیس کاملاً دست‌نخورده باقی می‌ماند.

4. **س: قوانین اعتبارسنجی کد تخفیف شامل چه مواردی است و چگونه ارزیابی می‌شوند؟**
   **ج:** تابع `validate_discount_code` بررسی می‌کند که:
   - کد تخفیف متعلق به همان هتل مورد رزرو باشد.
   - پرچم فعال بودن `is_active` برابر `True` باشد.
   - تاریخ جاری (`today`) در بازه مجاز `valid_from <= today <= valid_to` قرار داشته باشد.
   - در صورت تعیین سقف استفاده (`max_uses is not None`)، تعداد استفاده‌های قبلی `used_count` به سقف نرسیده باشد.

5. **س: چگونه از دسترسی کاربران مسافر به رزروهای یکدیگر جلوگیری کردید (Data Isolation)؟**
   **ج:** در اندپوینت‌های `GET /api/bookings/mine/` و `POST /api/bookings/{id}/cancel/`، کوئری‌های دیتابیس همواره با فیلتر صریح `guest=request.user` محدود شده‌اند. علاوه بر آن با استفاده از دکوراتور `@role_required("guest")`، احراز هویت و نقش کاربر بررسی می‌شود. بنابراین حتی اگر کاربری شناسه رزرو مسافر دیگری را ارسال کند، سیستم با خطای 404 (یا دسترسی غیرمجاز) مواجه شده و اطلاعات رزرو سایر افراد فاش نخواهد شد.

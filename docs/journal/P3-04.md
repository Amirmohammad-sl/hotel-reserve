## Why / design decisions (and alternatives rejected)
- **Database-Level Availability via `Prefetch` vs Python While Loops**: In Phase 2, `hotels_list_view` and `hotel_rooms_view` queried bookings in batch and ran a `while curr_day < check_out:` loop in Python for every room type. Using `Prefetch("room_types", queryset=RoomType.objects.with_availability(check_in, check_out))` pushes the entire date aggregation into SQL subqueries, drastically cutting down CPU overhead and eliminating 60+ lines of imperative view logic.
- **`with_min_price()` SQL aggregation vs Python `min()`**: The starting price ("From X Toman") is now calculated directly in the SQL `SELECT` via `Hotel.objects.with_min_price()` (`MIN(room_types__price_per_night)`), eliminating Python list comprehensions and memory consumption.
- **Preserving Domain Error Messages in `validate_discount_code`**: While `DiscountCode.objects.get_valid` returns the valid discount instance in a single query on the happy path, fallback inspection provides distinct error reasons ("inactive", "expired", "maximum redemptions") when a coupon is invalid. This keeps frontend user experience and API contract error payloads 100% backward compatible.
- **Tenant & Ownership Boundaries via `for_guest(user)`**: Centralising user filtering in `Booking.objects.for_guest(user)` prevents horizontal authorization leaks and avoids repetitive `filter(guest=request.user)` clauses across views.

## How it works (follow ONE request/click end to end)
1. **Hotel Search Request**:
   - A guest searches for hotels in Isfahan for dates `2026-11-13` to `2026-11-16` via `GET /api/hotels/?city=Isfahan&check_in=2026-11-13&check_out=2026-11-16`.
   - `hotels_list_view` builds a single query:
     ```python
     room_types_prefetch = Prefetch(
         "room_types",
         queryset=RoomType.objects.with_availability(check_in, check_out).prefetch_related("amenities")
     )
     hotels_qs = Hotel.objects.active().in_city("Isfahan").with_min_price().prefetch_related(room_types_prefetch)
     ```
   - Django executes optimized SQL querying only active hotels in Isfahan, annotating `min_price`, and prefetching room types with their SQL-calculated `available_count`.
   - Hotels without any available room type are excluded (satisfying the Phase 2 DoD invariant).
   - Response returns `{data: [{id, name, min_price, available: true, ...}]}`.

2. **Booking Quote and Creation**:
   - Guest requests quote via `POST /api/bookings/quote/`.
   - `calculate_booking_quote` executes `RoomType.objects.with_availability(check_in, check_out).filter(id=room_type.id)`.
   - If coupon code is entered, `DiscountCode.objects.get_valid(hotel, code)` validates the coupon in one ORM call.
   - Quote returns `{nights, subtotal, discount_amount, total_price, available}`.
   - On `POST /api/bookings/`, `create_booking` confirms inventory atomically and persists the reservation.

## Gotchas / things that surprised us
- **`Prefetch` with Annotated QuerySets**: When using `prefetch_related("room_types")`, Django would execute the default model queryset without availability annotations. Using `django.db.models.Prefetch("room_types", queryset=RoomType.objects.with_availability(...))` allowed each child object in `hotel.room_types.all()` to retain its `.available_count` attribute directly.
- **Cross-App QuerySet Composition**: In `backend/apps/hotels/models.py`, `RoomTypeQuerySet.with_availability` originally had raw SQL filter conditions for bookings (`status='confirmed'`, `check_in__lt=...`, `check_out__gt=...`). Refactoring it to `Booking.objects.active().overlapping(check_in, check_out)` coupled the two custom querysets cleanly while adhering to DRY.

2. **س: چرا در متد `hotels_list_view` از کلاس `django.db.models.Prefetch` استفاده کردیم به جای `prefetch_related("room_types")` ساده؟**
   **ج:** اگر صرفاً از نام فیلد رابطه‌ای (`"room_types"`) استفاده شود، جنگو کوئری پیش‌فرض مدل را اجرا می‌کند که شامل فیلدهای محاسبه‌شده مثل `reserved` و `available_count` نیست. با ساخت یک شیء `Prefetch` که کوئری‌ست آن برابر `RoomType.objects.with_availability(check_in, check_out)` است، به جنگو می‌گوییم که اتاق‌های مرتبط را همراه با این حاشیه‌نویسی‌ها (Annotations) واکشی کند تا در حلقه نتایج هر اتاق از قبل دارای ویژگی `available_count` آماده باشد.

3. **س: نحوه استفاده از `DiscountCode.objects.get_valid` در سرویس اعتبارسنجی چگونه طراحی شد تا پیام‌های خطای کلاینت حفظ شوند؟**
   **ج:** متد `get_valid` در صورتی که کد فعال، در بازه تاریخی معتبر و دارای سقف استفاده باقی‌مانده باشد، شیء تخفیف را در یک کوئری برمی‌گرداند. برای مسیر موفق (Happy path) مستقیماً از همین متد استفاده می‌شود. اما اگر خروجی `None` باشد، برای ارائه خطای دقیق به کاربر در پاسخ HTTP 400 (مثلاً تفکیک بین «کد منقضی شده»، «کد غیرفعال است» یا «سقف استفاده پر شده»)، بررسی جزئیات صورت می‌گیرد تا قرارداد API و رفتار فرانت‌اند هیچ تغییری نکند.

4. **س: متد `Booking.objects.for_guest(user)` چه مزیتی در ویوهای `my_bookings` و `booking_cancel` ایجاد می‌کند؟**
   **ج:** این متد مرز امنیتی مسافر را درون کوئری‌ست مدل کپسوله می‌کند. در صورت عدم استفاده از آن، هر ویو باید دستی شرط `filter(guest=request.user)` را بنویسد که در صورت فراموشی در یک اندپوینت جدید، ریسک نشت رزروهای سایر کاربران (Horizontal Privilege Escalation) را به همراه دارد. با `for_guest` این تضمین امنیتی در لایه منیجر به صورت استاندارد تأمین می‌شود.

5. **س: چگونه متد `RoomTypeQuerySet.with_availability` با متدهای `BookingQuerySet` ترکیب (Compose) شد؟**
   **ج:** در زیرکوئری (Subquery) محاسبه تعداد اتاق‌های رزروشده، به جای نوشتن شروط خام فیلتر `status=Booking.Status.CONFIRMED` و بررسی بازه تاریخی، از متدهای دامنه‌ای `Booking.objects.active().overlapping(check_in, check_out)` استفاده شد. این کار هماهنگی کاملی بین منیجرهای دو اپلیکیشن مختلف (`hotels` و `bookings`) ایجاد کرده و اصل DRY را تضمین می‌کند.

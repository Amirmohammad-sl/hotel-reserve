## What was done (3–6 bullets)
- Enhanced `scripts/restore_db.sh` to optionally accept a target database name as an argument (`scripts/restore_db.sh <file.sql> [target_db]`), defaulting to `DB_NAME` from `.env`.
- Added native PowerShell helper scripts `scripts/backup_db.ps1` and `scripts/restore_db.ps1` providing parity and seamless execution on Windows without requiring Git Bash path resolution.
- Executed `scripts/backup_db.sh phase1` to generate the official Phase 1 database backup `db_backup/hotel_db_phase1.sql` (54,336 bytes, 17 `CREATE TABLE` statements).
- Verified database restoration into an isolated scratch database (`hotel_restore_test`) using `scripts/restore_db.sh`, confirming all 17 relations and seed schemas restore with zero errors.
- Cleaned up scratch test database and verified all 43 backend test cases pass without regressions.

## Why / design decisions (and alternatives rejected)
- **Optional target database parameter in `restore_db.sh`**: The original script only allowed restoring into `$DB_NAME` from `.env`. Adding an optional `target_db` argument (`TARGET_DB="${2:-${DB_NAME:?DB_NAME missing}}"`) allows safe validation on temporary scratch databases without risking accidental overwrites or dropping active development databases.
- **Plain SQL dump (`pg_dump` with `--clean --if-exists`)**: Plain text SQL was chosen (and mandated by course requirements) so that the professor/evaluator can easily open and inspect schema and table definitions in any text editor or pgAdmin without proprietary tooling.
- **Adding PowerShell helpers (`.ps1`)**: Windows operators frequently run PowerShell as their native shell. While Git Bash supports `.sh`, providing `.ps1` equivalents ensures cross-platform consistency for both team operators regardless of their local terminal environment.
- **Omitting owner and privilege flags (`--no-owner --no-privileges`)**: Avoids hardcoding local OS/Postgres usernames or roles into the SQL dump, allowing any evaluator or colleague to restore the dump under their own PostgreSQL role.

## How it works (follow ONE request/click end to end)
1. The operator runs `scripts/backup_db.sh phase1` (or `.\scripts\backup_db.ps1 phase1`).
2. The script loads connection parameters (`DB_NAME`, `DB_USER`, `DB_PASSWORD`, `DB_HOST`, `DB_PORT`) from `backend/.env`.
3. `pg_dump` connects to the PostgreSQL instance and outputs clean DDL + data statements to `db_backup/hotel_db_phase1.sql`.
4. To test restoration, a scratch database `hotel_restore_test` is created via `createdb`.
5. Running `scripts/restore_db.sh db_backup/hotel_db_phase1.sql hotel_restore_test` connects to `hotel_restore_test` and executes the dump via `psql`.
6. Inspecting `\dt` in `hotel_restore_test` confirms all 17 public tables are successfully restored with proper schema structure.
7. The scratch database is cleanly dropped with `dropdb`.

## Gotchas / things that surprised us
- In PowerShell array syntax `@( (Join-Path $a "b"), (Join-Path $c "d") )`, omitting inner parentheses causes PowerShell to bind the trailing expression as an array argument to `ChildPath` of the first cmdlet instead of creating an array of two evaluated strings. Adding explicit parentheses resolved the binding error.
- Setting `--clean --if-exists` in `pg_dump` produces `DROP TABLE IF EXISTS` statements before creating tables, which guarantees that restoring into an existing database does not fail due to duplicate table collision errors.

## Viva Q&A (Persian, 3–5) — questions the professor could ask about this task
1. س: چرا در دستور `pg_dump` از فلگ‌های `--no-owner` و `--no-privileges` استفاده شده است؟
   ج: به دلیل اینکه مالک (Owner) جداول و دسترسی‌های گرنت‌شده (Privileges) وابسته به نام کاربر دیتابیس در سیستم محلی است. اگر این فلگ‌ها استفاده نشوند، هنگام بازگردانی فایل دامپ روی سیستم استاد یا ماشین دیگری که نام کاربری متفاوتی دارد، دستورات `ALTER OWNER TO ...` با خطا مواجه می‌شوند. این فلگ‌ها باعث قابلیت حمل (Portability) بالای فایل پشتیبان می‌شوند.
2. س: سوئیچ‌های `--clean` و `--if-exists` چه فایده‌ای در فایل پشتیبان دارند؟
   ج: سوئیچ `--clean` قبل از هر دستور `CREATE`، یک دستور `DROP` قرار می‌دهد تا در صورت وجود جداول قبلی در دیتابیس، ساختار قبلی پاک و جایگزین شود. سوئیچ `--if-exists` باعث می‌شود که عبارت `DROP TABLE IF EXISTS` تولید شود؛ در نتیجه اگر دیتابیس خالی باشد یا جدولی از قبل وجود نداشته باشد، اجرای اسکریپت با خطا مواجه نخواهد شد.
3. س: تفاوت دامپ متنی ساده (Plain SQL) با فرمت‌های باینری کاستوم (`-F c`) در PostgreSQL چیست و چرا در این پروژه فرمت Plain SQL انتخاب شد؟
   ج: فرمت باینری فشرده‌تر است و اجازه می‌دهد با `pg_restore` جداول را انتخابی بازگردانی کنیم، اما فقط با `pg_restore` قابل خواندن است. فرمت متنی ساده (Plain SQL) با هر ویرایشگر متنی، گیت (برای مقایسه diff در صورت نیاز) و دستور استاندارد `psql` قابل اجرا و بررسی است؛ از آنجا که طبق نیازمندی درس استاد باید بتواند فایل پشتیبان را بررسی کند، فرمت متنی استاندارد و خوانا ترجیح داده شده است.
4. س: چرا تست بازگردانی (Restore) در یک دیتابیس موقت مستقل (`hotel_restore_test`) انجام شد؟
   ج: برای اعتبارسنجی عملی فایل بکاپ بدون به خطر انداختن دیتابیس اصلی؛ این کار ثابت می‌کند که فایل بکاپ به تنهایی مستقل (self-contained) است و روی یک دیتابیس کاملاً خام و خالی می‌تواند تمام ۱۷ جدول و روابط را بدون کم و کاست بازسازی کند.

## Why / design decisions (and alternatives rejected)
- **Plain Django views & Forms vs DRF**: Adhered strictly to the course requirement (no DRF). Used `json_ok` and `json_error` envelopes from `apps.core.http` and `form_errors` for validation error payloads.
- **Batch booking query for hotel search**: Instead of querying bookings separately for each room type in each hotel ($N+1$ queries), we query all matching hotels with `prefetch_related("room_types")` and fetch overlapping confirmed bookings in a single query, grouping them in memory.
- **Availability calculation**: Checked every day in the interval `[check_in, check_out)` against confirmed bookings. Cancelled bookings (`status='cancelled'`) are explicitly excluded and do not occupy room inventory.

## How it works (follow ONE request/click end to end)
1. Guest sends `GET /api/hotels/?city=Tehran&check_in=2026-12-01&check_out=2026-12-05&guests=2`.
2. `hotels_list_view` binds `request.GET` to `SearchForm`. Form validates that check-in is not in the past and check-out is after check-in.
3. View queries active hotels in Tehran (`is_active=True`, `city__iexact='Tehran'`).
4. Overlapping confirmed bookings for all room types in those hotels during `[2026-12-01, 2026-12-05)` are fetched in one query.
5. For each hotel, room types are evaluated: capacity must be $\ge 2$, and available room count on all days in the range must be $\ge 1$.
6. If a hotel has at least one matching available room type, it is included in the response with `available: true` and `min_price`. Otherwise it is excluded (DoD).
7. View returns `{"data": [...]}` with status 200 via `json_ok`.

## Gotchas / things that surprised us
- In Django test client under Python 3.15, `store_rendered_templates` signal copier hits an incompatibility with `BaseContext.__copy__` when rendering templates. Since our views return `JsonResponse`, they are not affected, and we added a small compatibility patch for admin changelist test so local tests pass flawlessly under Python 3.15 while staying compatible with Python 3.12 in CI.

## Viva Q&A (Persian, 3–5) — questions the professor could ask about this task
1. **س: نحوه محاسبه ظرفیت خالی اتاق‌ها (Availability) در یک بازه زمانی چگونه پیاده‌سازی شده است؟**
   **ج:** برای هر روز در بازه اقامت `[check_in, check_out)`، تعداد رزروهای تاییدشده (`confirmed`) که با آن روز هم‌پوشانی دارند محاسبه می‌شود. بیشترین تعداد اتاق رزروشده در شلوغ‌ترین روز بازه از کل موجودی فیزیکی نوع اتاق (`quantity`) کسر می‌شود تا حداقل اتاق‌های آزاد در طول کل اقامت به دست آید. رزروهای لغو شده (`cancelled`) آزاد شده و محاسبه نمی‌شوند.

2. **س: چگونه جلوی بروز مشکل N+1 کوئری در صفحه جستجوی هتل‌ها را گرفتید؟**
   **ج:** هتل‌ها را همراه با نوع اتاق‌هایشان با `prefetch_related("room_types")` واکشی می‌کنیم. سپس تمام رزروهای تاییدشده مربوط به این اتاق‌ها در بازه تاریخی مشخص‌شده، در یک کوئری واحد از دیتابیس دریافت شده و در پایتون بر اساس `room_type_id` دسته‌بندی می‌شوند؛ به جای اینکه به ازای هر هتل و هر اتاق یک کوئری جداگانه به دیتابیس زده شود.

3. **س: چرا بدون استفاده از DRF، اعتبارسنجی پارامترهای GET را در فرم‌های جنگو انجام دادید؟**
   **ج:** طبق الزامات درس، استفاده از DRF ممنوع است. بنابراین از `forms.Form` استاندارد جنگو (`SearchForm`) استفاده کردیم که داده‌های `request.GET` را تمیز، نوع داده‌ها را بررسی و قواعد منطقی بازه تاریخی (مانند عدم انتخاب تاریخ گذشته و `check_in < check_out`) را اعتبارسنجی می‌کند و در صورت بروز خطا، پیام‌های متناسب با ساختار خطاها تولید می‌کند.

4. **س: وقتی کاربر تاریخ وارد نکرده باشد، جستجو و فیلتر هتل‌ها چه تفاوتی می‌کند؟**
   **ج:** بدون تاریخ، هتل‌های فعال بر اساس شهر، نام یا متن `q` و بازه قیمت فیلتر می‌شوند و فیلتر موجودی رزرو اعمال نمی‌گردد (چون بازه زمانی وجود ندارد)، و حداقل قیمت (`min_price`) هتل بازگردانده می‌شود. اما با ارسال تاریخ، هتل‌هایی که هیچ اتاق خالی برای آن تاریخ ندارند کاملاً از نتایج حذف می‌شوند.

# P2-10 — Test data: `seed_demo` command + fixtures
- Author: A (Amirmohammad Soleimani)   · Reviewer: B (Mahdi Moradi)   · PR: TBD   · Date: 2026-11-07

## What was done (3–6 bullets)
- Implemented `seed_demo` custom Django management command in `backend/apps/core/management/commands/seed_demo.py` to satisfy course requirement for pre-populated test data entry.
- Created idempotent fixtures with realistic Iranian hotel data: 2 managers (`manager1`, `manager2`), 5 guests (`guest1` to `guest5`), 7 amenities, 7 hotels in 4 major cities (Tehran, Isfahan, Shiraz, Yazd), 17 room types (2–3 per hotel) with linked amenities, and active discount codes.
- Generated 21 realistic bookings distributed across all states: 7 past (completed), 5 current (active/in-house), 5 future (confirmed upcoming), and 4 cancelled bookings (with `cancelled_at` timestamps) with accurate financial snapshots (`price_per_night_snapshot`, `subtotal`, `discount_amount`, `total_price`).
- Implemented `--reset` flag allowing developers and evaluators to wipe and rebuild clean test data atomically using `transaction.atomic()`.
- Guaranteed idempotency: executing `python manage.py seed_demo` repeatedly checks for existing records (via unique keys / constraints) and preserves data without duplicating records.
- Added comprehensive automated test suite in `apps/core/tests.py` covering model counts, password authentications, idempotency, and `--reset` flag behavior.
- Documented demo accounts, passwords, and command usage in `README.md`.

## Why / design decisions (and alternatives rejected)
- **Django Management Command vs Static JSON Fixtures**: Static fixture JSON files (`loaddata`) break easily across model changes, cannot easily compute dynamic relative dates (e.g. past vs future relative to `date.today()`), and fail to run custom business logic (e.g. password hashing with Django's Argon2/PBKDF2 hasher). A custom Python command is dynamic, robust, and supports `--reset`.
- **Dynamic Relative Dates**: By anchoring check-in and check-out dates relative to `date.today()`, test bookings always remain validly categorized into past, current, and future regardless of what day the professor runs the evaluation demo.
- **Atomic Execution & Safe Reset**: Using `transaction.atomic()` guarantees that if an unexpected error occurs during data entry, the database rolls back cleanly. The `--reset` option specifically deletes demo-tagged entities without dropping arbitrary user data.

## Viva defense questions & answers (سوالات روز دفاع و پاسخ‌ها)

### ۱. چرا به جای استفاده از `fixtures` پیش‌فرض جنگو (`dumpdata` / `loaddata`)، یک دستور مدیریتی اختصاصی (`seed_demo`) نوشتید؟
**پاسخ:** فایل‌های `json` در `loaddata` دارای تاریخ‌های ایستا و استاتیک هستند. اگر ارزیاب یا استاد پروژه را دو هفته یا یک ماه دیگر اجرا کند، تمام رزروها ممکن است در گذشته قرار بگیرند و هیچ رزرو فعلی (Current) یا آینده‌ای وجود نداشته باشد. با دستور پایتونی `seed_demo`، تاریخ‌های ورود و خروج به صورت پویا نسبت به `date.today()` تنظیم می‌شوند و همواره رزروهای گذشته، حال و آینده به درستی نمایش داده می‌شوند. همچنین رمزهای عبور به کمک سیستم استاندارد هش پسورد جنگو (`create_user`) ساخته می‌شوند و فلگ `--reset` نیز برای پاکسازی و بازسازی سریع دیتابیس فراهم است.

### ۲. خاصیت Idempotent (شناسایی تکرار) در این دستور چگونه پیاده‌سازی و تضمین شده است؟
**پاسخ:** برای کاربران و امکانات، ابتدا وجود نام‌کاربری یا نام امکان بررسی شده و از ساخت مجدد جلوگیری می‌شود. برای هتل‌ها و انواع اتاق‌ها از متد `get_or_create` به همراه قیدهای یکتایی (`name` برای هتل و جفت `hotel + title` برای نوع اتاق) استفاده شده است. برای رزروها نیز بر اساس ۴ ویژگی یکتا (مهمان، نوع اتاق، تاریخ ورود و تاریخ خروج) جستجو انجام می‌شود تا در صورت وجود رکورد، رکورد جدیدی اضافه نشود. این رفتار توسط تست `test_seed_demo_idempotency_does_not_duplicate` اعتبارسنجی شده است.

### ۳. در سناریوی رزروها، داده‌های مالی نظیر تخفیف و اسنپ‌شات قیمت چگونه ذخیره شده‌اند؟
**پاسخ:** مطابق قرارداد داده‌ای فاز ۱ (`docs/DATA_MODEL.md`)، در هر رزرو فیلد `price_per_night_snapshot` قیمت پایه هر شب در لحظه رزرو را نگه‌داری می‌کند تا تغییرات آتی قیمت اتاق روی رزروهای قبلی تاثیری نگذارد. همچنین فیلد `subtotal` برابر با `nights * rooms_count * price_per_night` است. در صورتی که کد تخفیف اعمال شده باشد، فیلد `discount_code` ارجاع داده شده، `discount_amount` کسر شده و مبلغ نهایی در `total_price` قرار می‌گیرد. همچنین برای رزروهای تایید شده، شمارنده `used_count` کد تخفیف به‌روزرسانی می‌شود.

### ۴. برای رزروهای لغو شده (Cancelled)، چه الزامات داده‌ای در `seed_demo` رعایت شده است؟
**پاسخ:** رزروهای لغو شده دارای وضعیت `status = Booking.Status.CANCELLED` هستند و فیلد `cancelled_at` آن‌ها با یک زمان معتبر در گذشته مقداردهی شده است. این امر باعث می‌شود هنگام محاسبه ظرفیت روزانه اتاق‌ها در اندپوینت‌های جستجو و تقویم در دسترس بودن مدیر، این رزروها به درستی نادیده گرفته شوند و ظرفیت هتل را اشغال نکنند.

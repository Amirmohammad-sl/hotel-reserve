# P1-03 — User model fields and manager skeleton

## What was done (3–6 bullets)
- Expanded `accounts.User` model with required domain fields: `role` (`manager` or `guest`, default `guest`), `phone` (blank charfield), `email` (unique, required), and `email_verified` (boolean, default False).
- Added `Role(models.TextChoices)` and convenient boolean properties `is_manager` and `is_guest`.
- Implemented `UserManager` skeleton subclassing Django's `UserManager` with customized `create_user` and `create_superuser` defaults for user roles.
- Created and applied PostgreSQL migration `0002_alter_user_options_alter_user_managers_and_more.py`.
- Configured `CustomUserAdmin` in `apps/accounts/admin.py` with custom fieldsets, add_fieldsets, search fields, and filters.
- Added comprehensive unit tests in `apps/accounts/tests.py` verifying defaults, constraints, helpers, and admin integration (12 total tests passing).

## Why / design decisions (and alternatives rejected)
- **`models.TextChoices` for roles**: Used modern Django `TextChoices` instead of loose tuples or integers. This provides strongly typed choices (`User.Role.MANAGER`, `User.Role.GUEST`) and auto-generates readable labels.
- **`unique=True` on `email`**: The course and `DATA_MODEL.md` require email-based unique identification. We kept `AbstractUser`'s username field while making `email` unique and non-blank.
- **Custom `UserManager` skeleton**: Subclassing `django.contrib.auth.models.UserManager` ensures seamless integration with Django's built-in authentication and auth forms while allowing P3-01 to add domain-specific query methods cleanly later.
- **Explicit `CustomUserAdmin` configuration**: Standard `UserAdmin` ignores custom fields in `add_fieldsets`. Registering custom `fieldsets` and `add_fieldsets` ensures that Django admin users can create and manage guests and managers directly.

## How it works (follow ONE request/click end to end)
- When a user registration or user creation request is processed:
  1. `User.objects.create_user(username, email, password, **extra)` is invoked.
  2. The custom `UserManager` sets `role="guest"` by default if not specified.
  3. The model saves the record to PostgreSQL, verifying that `email` is provided and unique across all users.
  4. At runtime, business logic or permission decorators can check `user.is_manager` or `user.is_guest` directly.
- In Django admin (`/admin/accounts/user/add/`):
  1. The administrator enters username, password, email, role (`manager` or `guest`), phone, and verification status.
  2. `CustomUserAdmin.add_fieldsets` displays these fields cleanly, allowing immediate assignment of user roles.

## Gotchas / things that surprised us
- Adding `unique=True` on an existing table's column can fail if rows already have NULL or duplicate values. Because we are in early development on a clean PostgreSQL database (0 rows), the migration applied cleanly without needing a multi-step data migration.

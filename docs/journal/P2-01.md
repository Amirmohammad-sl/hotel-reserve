## Why / design decisions (and alternatives rejected)
- **JSON Error Envelopes for API paths**: Instead of a global exception middleware that could interfere with Django admin or debug tools, we implemented standard Django handlers (`handler404`, `handler500`, etc.) in `config/urls.py` with path inspection (`request.path.startswith("/api/")`). This ensures API clients (React frontend) always receive structured JSON (`{"message": "..."}`) while admin or HTML routes preserve standard Django behavior.
- **Support for CBV and FBV in decorators**: Decorators use `_extract_request` to locate the `HttpRequest` object whether the decorator is applied to a standalone view function `view(request, ...)` or a class-based view method `get(self, request, ...)`.
- **BREACH Defense in CSRF Token Endpoint**: Django 5.x uses masked tokens (`get_token`) to prevent BREACH attacks while keeping a 32-character secret in the cookie. The test verifies that `_unmask_cipher_token(masked_token)` matches the cookie secret.
- **Form Error Normalization**: Django forms produce `ErrorDict` and `ErrorList` objects containing lazy validation strings. `form_errors` extracts strings into pure Python lists of strings, including non-field errors under `__all__`, matching `API_CONTRACT.md`.

## How it works (follow ONE request/click end to end)
1. **Frontend CSRF initialization**:
   - The React frontend makes a `GET /api/auth/csrf/` call on initialization.
   - Django executes `csrf_token_view` decorated with `@ensure_csrf_cookie`.
   - Django generates a CSRF cookie (`csrftoken`) and returns `{"data": {"csrfToken": "..."}}`.
   - Subsequent `POST`/`PUT`/`DELETE` calls read this token and attach it as `X-CSRFToken` in request headers.
2. **Access Control**:
   - When a request hits a protected view decorated with `@role_required("manager")`:
   - If `request.user.is_authenticated` is False → returns 401 JSON `{"message": "Authentication required."}`.
   - If `request.user.role != "manager"` → returns 403 JSON `{"message": "Permission denied."}`.
   - If valid manager → proceeds to the view function.

## Gotchas / things that surprised us
- In Django 5.x, the CSRF token returned by `get_token(request)` is a 64-character masked token (ciphered per request to mitigate BREACH compression attacks), while the cookie contains the 32-character raw token secret. They do not match verbatim by equality, but unmasking via `_unmask_cipher_token` validates exact match.
- Ensuring decorators work whether applied to function views or CBV dispatch methods requires careful handling of argument unpacking (`args[0]` vs `args[1]`).

1. س: چرا به جای استفاده از جنگو رست فریم‌ورک (DRF) از ویوها و دکوراتورهای سفارشی جنگو برای بازگرداندن JSON استفاده کردید؟
   ج: طبق تصمیمات معماری پروژه (D-002) و سرفصل‌های رسمی درس برنامه‌نویسی وب، هدف تسلط عمیق بر مفاهیم پایه فریم‌ورک جنگو شامل Forms، Views، Decorators و Sessions بدون تکیه بر فریم‌ورک‌های واسط مانند DRF است. دکوراتورهای `@login_required_json` و `@role_required` و توابع کمکی `json_ok` و `json_error` ساختار پاسخ‌ها را کاملاً یکپارچه و منطبق بر استاندارد پروژه پیاده‌سازی می‌کنند.
2. س: تفاوت نحوه کارکرد دکوراتور `login_required` پیش‌فرض جنگو با `login_required_json` شما چیست؟
   ج: دکوراتور استاندارد `login_required` جنگو در صورت احراز هویت نشدن کاربر، او را با کد ۳۰۲ به صفحه فرم ورود (HTML) ریدایرکت می‌کند که برای برنامه‌های تک‌صفحه‌ای (SPA / React) نامناسب است. دکوراتور سفارشی ما با بازگرداندن کد وضعیت استاندارد ۴۰۱ (Unauthorized) و پاسخ JSON ساختاریافته به کلاینت فرانت‌اند اجازه می‌دهد وضعیت عدم احراز هویت را شناسایی و دیالوگ ورود یا ریدایرکت مناسب را مدیریت کند.
3. س: دکوراتور `role_required` چگونه نقش‌های مجاز را کنترل می‌کند و چه کدهای وضعیتی برمی‌گرداند؟
   ج: این دکوراتور می‌تواند یک یا چند نقش مجاز (مانند `"manager"` یا `"guest"`) دریافت کند. ابتدا بررسی می‌کند که کاربر احراز هویت شده باشد؛ اگر نشده باشد کد ۴۰۱ برمی‌گرداند. سپس فیلد `role` از مدل اختصاصی کاربر (`User`) را با نقش‌های مجاز مقایسه می‌کند؛ در صورت عدم تطابق، کد وضعیت استاندارد ۴۰۳ (Forbidden) به همراه پیام خطا در پاکت استاندارد JSON بازگردانده می‌شود. در صورت تطابق، درخواست به ویو ارسال می‌شود.
4. س: چرا هندلرهای خطای ۴۰۴ و ۵۰۰ به جای بازگرداندن قالب‌های متنی جنگو، خطاها را با JSON برمی‌گردانند؟
   ج: تمام درخواست‌هایی که کلاینت فرانت‌اند به مسیرهای `/api/` ارسال می‌کند به صورت ایجکس/Fetch هستند و کلاینت انتظار دریافت شیء JSON دارد. اگر یک اندپوینت ناموجود صدا زده شود، ارسال صفحه خطای HTML پیش‌فرض جنگو باعث بروز خطای parse در فرانت‌اند می‌شود. به همین دلیل در هندلرهای اختصاصی بررسی کردیم که اگر مسیر درخواست با `/api/` آغاز شده باشد، خطای ۴۰۴ یا ۵۰۰ به صورت JSON بازگردانده شود و برای سایر مسیرها (مثل بخش‌های پیش‌فرض جنگو) همان رفتار استاندارد HTML حفظ شود.
5. س: اندپوینت `/api/auth/csrf/` چه نقشی دارد و چگونه از حملات CSRF محافظت می‌کند؟
   ج: در معماری SPA، کلاینت برای ارسال درخواست‌های تغییردهنده (POST/PUT/DELETE) به توکن ضد جعل CSRF نیاز دارد. اندپوینت `/api/auth/csrf/` با دکوراتور `@ensure_csrf_cookie` کوکی `csrftoken` را برای مرورگر کاربر صادر و تنظیم می‌کند و مقدار توکن را نیز در پاسخ JSON قرار می‌دهد تا فرانت‌اند بتواند آن را در هدر `X-CSRFToken` درخواست‌های بعدی ارسال کند.

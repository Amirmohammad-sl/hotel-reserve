# P3-05 — Concurrency-safe booking

## What was done (3–6 bullets)
- Enforced pessimistic row-level locking via `select_for_update()` on the `RoomType` instance within `transaction.atomic()` inside `create_booking` (`backend/apps/bookings/services.py`).
- Added serialised row locking on `DiscountCode` inside `create_booking` when a coupon is supplied, verifying `max_uses` limits before redemption.
- Updated `used_count` increments and decrements to execute atomically using Django's `F("used_count")` expressions.
- Protected `cancel_booking` with `select_for_update()` on the `Booking` row to eliminate race conditions on cancellation and coupon restoration.
- Implemented multithreaded concurrency tests in `BookingConcurrencyTests(TransactionTestCase)` (`backend/apps/bookings/tests.py`) simulating simultaneous booking attempts against the last available room and concurrent discount code redemptions.

## Why / design decisions (and alternatives rejected)
- **Pessimistic Locking (`SELECT FOR UPDATE`) vs Optimistic Locking (`version` column)**:
  - *Alternative rejected*: Optimistic concurrency control (OCC) checks a version integer upon update and fails if another worker bumped it. In high-traffic scenarios (e.g. flash sales on hotel rooms), OCC incurs high retry rates, wasted work, and degraded user experience.
  - *Chosen approach*: Pessimistic locking locks the specific `RoomType` row in PostgreSQL. Any overlapping booking request for that room type waits on the lock, and immediately upon acquisition executes the availability subquery with the newly committed state, detecting exhausted inventory without phantom overbooking.
- **Lock Ordering to Prevent Deadlocks**:
  - Whenever multiple resources are locked within a transaction, lock acquisition order must remain strictly consistent. In `create_booking`, the transaction locks `RoomType` first, followed by `DiscountCode` (if present). No other transaction acquires these locks in reverse order, preventing database deadlocks.
- **Atomic Counter Updates via `F()` Expressions**:
  - Using `models.F("used_count") + 1` pushes the addition operation directly to the database engine (`SET used_count = used_count + 1`), avoiding Python-side read-modify-write lost-update races.
- **Avoiding `select_related` on Outer Joins with `FOR UPDATE`**:
  - PostgreSQL throws `NotSupportedError: FOR UPDATE cannot be applied to the nullable side of an outer join` when `select_related()` is used on a nullable foreign key (such as `discount_code` on `Booking`). Omitting `select_related` on nullable relations when acquiring row locks ensures clean SQL generation while retaining access to FK ids.

## How it works (follow ONE request/click end to end)
1. **Concurrent Request Arrival**:
   - Two guests, Alice and Bob, both submit `POST /api/bookings/` for the last available room (`quantity=1`) of "Royal Suite" for check-in `2026-11-20` to `2026-11-22` at the exact same millisecond.
2. **First Transaction Acquisition**:
   - Alice's request enters `transaction.atomic()` in `create_booking`.
   - Alice executes `locked_room_type = RoomType.objects.select_for_update().get(id=room_type.id)`.
   - PostgreSQL grants an exclusive row-level lock on the `RoomType` row to Alice's transaction.
3. **Second Transaction Wait**:
   - Bob's request enters `transaction.atomic()` and attempts `RoomType.objects.select_for_update().get(...)`.
   - PostgreSQL blocks Bob's worker thread, waiting for Alice's transaction to commit or roll back.
4. **Availability & Confirmation (Alice)**:
   - Alice evaluates `calculate_booking_quote`, which calculates `available_count = 1`.
   - The booking is created, and Alice's transaction commits. The lock on `RoomType` is released.
   - Alice receives HTTP 201 Created with booking details.
5. **Post-Lock Evaluation (Bob)**:
   - Bob's thread unblocks immediately upon Alice's commit and receives `locked_room_type`.
   - Bob evaluates `calculate_booking_quote`. Because Alice's booking is committed, the `overlapping_bookings` subquery counts Alice's room, resulting in `available_count = 0`.
   - `quote["available"]` evaluates to `False`.
   - `create_booking` raises `AvailabilityConflictError`.
   - The view layer catches `AvailabilityConflictError` and returns HTTP 409 Conflict with an informative message.
   - **Zero overbooking occurs.**

## Gotchas / things that surprised us
- **PostgreSQL `FOR UPDATE` on Nullable Outer Joins**: When writing `Booking.objects.select_for_update().filter(id=booking.id).select_related("room_type", "discount_code")`, PostgreSQL failed with:
  `django.db.utils.NotSupportedError: FOR UPDATE cannot be applied to the nullable side of an outer join`.
  Because `discount_code` is nullable, Django generates a `LEFT OUTER JOIN`. PostgreSQL refuses to lock rows where columns could be NULL from an outer join. Removing `select_related` resolved the issue cleanly while keeping locking logic 100% sound.
- **Django `TestCase` vs `TransactionTestCase` for Multi-Threading**: Standard `TestCase` wraps each test method in an atomic database transaction and rolls it back at the end. Because other threads run on distinct database connections, they cannot see uncommitted data from the main test thread. Using `TransactionTestCase` allows real database commits across distinct thread connections, enabling true concurrency and lock verification.

## Viva Q&A (Persian, 3–5) — questions the professor could ask about this task
1. **س: پدیده Overbooking در سیستم‌های رزرواسیون چگونه رخ می‌دهد و چرا بررسی ساده ظرفیت قبل از ذخیره (Check-Then-Act) آسیب‌پذیر به Race Condition است؟**
   **ج:** در معماری‌های وب چندنخی، اگر دو مسافر همزمان درخواست رزرو آخرین اتاق خالی را ارسال کنند، هر دو درخواست ممکن است کوئری ظرفیت را همزمان بخوانند و ببینند ۱ اتاق خالی است (Time-of-Check). سپس هر دو درخواست اقدام به صدور رزرو و ثبت در دیتابیس می‌کنند (Time-of-Action). در نتیجه ۲ رزرو برای ۱ اتاق صادر می‌شود (Overbooking). این مشکل به دلیل عدم همگام‌سازی تراکنش‌ها و شرایط رقابتی (Race Condition) رخ می‌دهد.

2. **س: تفاوت قفل‌گذاری بدبینانه (Pessimistic Locking) با خوش‌بینانه (Optimistic Locking) چیست و چرا در این پروژه از `select_for_update()` استفاده شد؟**
   **ج:** در قفل‌گذاری خوش‌بینانه (OCC)، بدون معطل کردن دیگران فرض می‌شود تداخلی پیش نمی‌آید و فقط در زمان ذخیره، فیلد Version چک می‌شود. اگر تداخل رخ داده باشد کل عملیات Rollback شده و کاربر با خطا مواجه می‌شود که در رزرو اتاق و رویدادهای پرتقاضا، حجم بالایی از شکست تراکنش ایجاد می‌کند. در مقابل، قفل‌گذاری بدبینانه با `SELECT FOR UPDATE` ردیف نوع اتاق (`RoomType`) را در سطح پایگاه داده قفل می‌کند. تراکنش دوم پشت قفل منتظر می‌ماند و به محض اتمام تراکنش اول، وضعیت جدید و واقعی ظرفیت را بررسی می‌کند و از ایجاد رزرو مازاد جلوگیری می‌نماید.

3. **س: چرا در این تسک برای به‌روزرسانی فیلد `used_count` در مدل `DiscountCode` از عبارت `F()` جنگو استفاده شد؟**
   **ج:** در پایتون، عملیات `discount.used_count += 1` ابتدا مقدار فعلی را از رم می‌خواند و پس از اضافه کردن یک واحد، آن را در دیتابیس Save می‌کند. اگر دو درخواست همزمان این کار را انجام دهند، مقدار رم هر دو یکسان بوده و به جای ۲ بار افزایش، فقط ۱ بار فیلد زیاد می‌شود (Lost Update). با استفاده از `F("used_count") + 1`، عملیات جمع مستقیماً به دستور SQL منتقل می‌شود (`UPDATE ... SET used_count = used_count + 1`) که در سطح دیتابیس کاملاً اتمیک و امن است.

4. **س: خطای `FOR UPDATE cannot be applied to the nullable side of an outer join` در پستگرس چیست و چگونه در کد حل شد؟**
   **ج:** در پایگاه داده PostgreSQL، اعمال قفل سطری `FOR UPDATE` روی جداولی که از طریق `LEFT OUTER JOIN` پیوند خورده‌اند و ممکن است سطرهای سمت راست آن‌ها `NULL` باشد مجاز نیست. از آنجا که فیلد `discount_code` در مدل `Booking` دارای `null=True` است، استفاده از `select_related("discount_code")` همراه با `select_for_update()` این استثنا را ایجاد می‌کرد. با حذف `select_related` و واکشی مستقیم فیلدهای کلید خارجی موجود روی خود مدل `Booking`، کوئری به شکل یک `SELECT FOR UPDATE` تک‌جدولی ساده و استاندارد درآمد و مشکل رفع شد.

5. **س: چرا برای نوشتن تست‌های چندنخی همزمانی از `TransactionTestCase` استفاده شد و نه `TestCase` عادی جنگو؟**
   **ج:** کلاس `TestCase` پیش‌فرض جنگو تمام عملیات تست را داخل یک تراکنش فراگیر (Outer Transaction) اجرا کرده و در انتها آن را Rollback می‌کند. این تراکنش در کانکشن تِرِد اصلی باز است. در تست‌های همزمانی، ترد‌های فرعی کانکشن‌های مجزایی به دیتابیس باز می‌کنند و به دلیل ایزولاسیون تراکنش‌ها نمی‌توانند تغییرات تِرِد اصلی را ببینند. کلاس `TransactionTestCase` تراکنش سراسری ایجاد نمی‌کند و اجازه ثبت و مشاهده واقعی تغییرات در سطح دیتابیس را به چندین ترد مجزا می‌دهد.

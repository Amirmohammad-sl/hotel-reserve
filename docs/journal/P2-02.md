## What was done (3–6 bullets)
- Implemented `RegisterForm` in `apps/accounts/forms.py` with email and username uniqueness checks, password confirmation, role validation (`guest`/`manager`), and integration with Django's password validators.
- Implemented `LoginForm` in `apps/accounts/forms.py` accepting either username or email (`username_or_email`), supporting `remember_me` session expiration, and returning targeted field errors on `password` when a password is incorrect.
- Added serialization helper `user_to_dict` guaranteeing exact alignment with `docs/API_CONTRACT.md` schema (`{id, username, email, role, email_verified}`).
- Implemented views `register_view` (HTTP 201), `login_view` (HTTP 200 with session initiation), `logout_view` (HTTP 200 protected by `@login_required_json`), and `me_view` (HTTP 200 returning user or `{"data": null}`) in `apps/accounts/views.py`.
- Mounted authentication routes in `apps/accounts/urls.py` under `/api/auth/`.
- Created comprehensive test suite (31 tests in `apps/accounts/tests.py`) covering form validation, views, session persistence, cookie expiration, error envelopes, and full `Register → Login → Me → Logout` lifecycle.

## Why / design decisions (and alternatives rejected)
- **Plain Django Forms & Views instead of DRF Serializers**: Consistent with course requirements and architectural decision D-002, we utilized pure Django `Form` classes and `JsonResponse` envelopes. Form errors are transformed via `form_errors(form)` from P2-01 into the uniform contract format.
- **Support for Username or Email Login**: Users can log in using either their registered username or their email address. `LoginForm` resolves the user record via `Q(username__iexact=...) | Q(email__iexact=...)`.
- **Targeted Field Errors for DoD Compliance**: The task definition of done requires that an incorrect password yields an HTTP 400 response with field errors. `LoginForm` verifies whether the user exists first and specifically attributes invalid passwords to `password`, rather than collapsing everything into a vague generic non-field error.
- **Session Duration Control via `remember_me`**: When `remember_me` is checked, the session expiry is set to two weeks (`1209600` seconds). When unchecked, `request.session.set_expiry(0)` ensures the cookie expires immediately when the browser session terminates.
- **Anonymous State on `/api/auth/me/`**: Conforming strictly to `API_CONTRACT.md`, unauthenticated calls to `/api/auth/me/` return HTTP 200 with `{"data": null}` rather than a 401 error, enabling the frontend SPA to detect initial authentication status without throwing network errors.

## How it works (follow ONE request/click end to end)
1. **User Registration**:
   - Client sends `POST /api/auth/register/` with `{"username": "ali", "email": "ali@example.com", "password": "...", "password2": "...", "role": "guest"}`.
   - `register_view` parses JSON and validates data via `RegisterForm`.
   - On validity, `User.objects.create_user(...)` creates the record in PostgreSQL, and the endpoint returns HTTP 201 with `{id, username, email, role, email_verified}`.
2. **User Login**:
   - Client sends `POST /api/auth/login/` with `{"username_or_email": "ali@example.com", "password": "...", "remember_me": true}` along with the `X-CSRFToken` header.
   - `login_view` validates credentials via `LoginForm` and calls `django.contrib.auth.login(request, user)`.
   - Django issues a `sessionid` cookie in the HTTP response headers.
3. **Session Verification**:
   - Client makes `GET /api/auth/me/` with the session cookie.
   - `me_view` detects `request.user.is_authenticated == True` and returns `{"data": {...}}`.
4. **User Logout**:
   - Client sends `POST /api/auth/logout/`.
   - `logout_view` flushes the session via `django.contrib.auth.logout(request)` and returns HTTP 200.

## Gotchas / things that surprised us
- In Django's default `ModelBackend`, `authenticate()` calls `user.can_authenticate()`, which returns `False` for inactive users (`is_active=False`) and returns `None`. To reliably distinguish between a wrong password and an inactive account, `LoginForm` explicitly tests `user_obj.check_password(password)` before verifying `user_obj.is_active`.
- `request.session.get_expire_at_browser_close()` returns `True` when `set_expiry(0)` is invoked, ensuring standard cookie semantics when `remember_me` is False.

## Viva Q&A (Persian, 3–5) — questions the professor could ask about this task
1. س: چرا برای سیستم احراز هویت به جای JWT از Session Cookie جنگو استفاده کردید؟
   ج: بر اساس سرفصل‌های رسمی درس برنامه‌نویسی وب و تصمیم معماری D-003، هدف پروژه پیاده‌سازی و درک مدیریت Session و Cookie در سمت سرور و هماهنگی با مکانیزم حفاظت از جعل CSRF است. در احراز هویت با سشن، وضعیت ورود کاربر در پایگاه داده جنگو نگهداری شده و شناسه امن `sessionid` در کوکی مرورگر ذخیره می‌شود؛ این روش نیازی به ذخیره‌سازی توکن در `localStorage` که در برابر حملات XSS آسیب‌پذیر است ندارد و امکان ابطال آنی سشن توسط سرور (مثلاً هنگام خروج) را فراهم می‌کند.
2. س: فرم `LoginForm` چگونه امکان ورود همزمان با ایمیل یا نام کاربری را پشتیبانی می‌کند؟
   ج: در متد `clean` فرم `LoginForm`، ورودی `username_or_email` دریافت شده و یک کوئری با عملگر `Q` جنگو به صورت `Q(username__iexact=identifier) | Q(email__iexact=identifier)` اجرا می‌شود. اگر کاربری یافت شد، تابع استاندارد `authenticate` با `username` اصلی آن کاربر و گذرواژه فراخوانی می‌شود. این کار اجازه می‌دهد کاربر بدون وابستگی به فیلد ورودی به راحتی با هر دو شناسه وارد شود.
3. س: گزینه `remember_me` چگونه در جنگو مدیریت و تنظیم می‌شود؟
   ج: از طریق متد `request.session.set_expiry(value)`. در صورتی که کاربر گزینه مرا به خاطر بسپار را علامت زده باشد، مقدار انقضا برابر ۲ هفته (۱۲۰۹۶۰۰ ثانیه معادل مقدار پیش‌فرض `SESSION_COOKIE_AGE`) قرار می‌گیرد تا کوکی پایدار بماند. در غیر این صورت مقدار `0` پاس داده می‌شود که به مرورگر می‌گوید کوکی از نوع Session بوده و با بستن مرورگر به طور خودکار منقضی و حذف شود.
4. س: چرا ویوی `/api/auth/me/` در صورت عدم ورود کاربر به جای خطای ۴۰۱ مقدار `{"data": null}` برمی‌گرداند؟
   ج: طبق قرارداد پروژه (`docs/API_CONTRACT.md`)، کلاینت فرانت‌اند (React) هنگام بارگذاری اولیه صفحه باید وضعیت لاگین بودن کاربر را بسنجد. اگر اندپوینت وضعیت ناشناس را خطای ۴۰۱ تلقی کند، در کنسول مرورگر خطای شبکه ثبت می‌شود؛ در حالی که ناشناس بودن یک حالت کاملاً طبیعی و مورد انتظار است. با بازگرداندن وضعیت ۲۰۰ و داده `null`، فرانت‌اند به سادگی و بدون تولید خطای اضافی متوجه می‌شود که کاربر باید به عنوان مهمان نمایش داده شود.
5. س: برای برآورده کردن شرط DoD تسک مبنی بر ایجاد خطای فیلد روی پسورد در صورت اشتباه بودن رمز، چه تمهیدی اندیشیدید؟
   ج: به جای بازگرداندن خطای کلی فرم در `__all__`، در فرم `LoginForm` ابتدا وجود کاربر را استعلام می‌کنیم؛ اگر کاربر وجود نداشته باشد خطا روی فیلد `username_or_email` درج می‌شود. اما اگر کاربر وجود داشته و تابع `check_password` مقدار غلط برگرداند، با استفاده از `self.add_error("password", "Invalid password.")` خطا مستقیماً روی فیلد `password` ست می‌شود و خروجی ۴۰۰ با کلید `errors.password` تولید می‌گردد.

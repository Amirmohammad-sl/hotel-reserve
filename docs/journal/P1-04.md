## Why / design decisions (and alternatives rejected)
- **Database constraints at ORM level**: We added both validation validators (`MinValueValidator`) and database-level `CheckConstraint` and `UniqueConstraint`. This guarantees data integrity even if objects are manipulated outside Django forms (e.g. bulk operations or scripts).
- **Composite unique constraint on `(hotel, title)`**: Using `models.UniqueConstraint(fields=["hotel", "title"])` prevents two room types in the same hotel from sharing the exact same title, while allowing distinct hotels to each have a "Deluxe Suite" or "Standard Room".
- **Money stored as integer Toman (`PositiveBigIntegerField`)**: Adhering to decision D-004 avoids decimal rounding errors and currency conversion ambiguities.
- **Index on `city`**: Since guest searches will predominantly filter by hotel destination city (`/api/hotels/?city=...`), creating a database B-Tree index on `Hotel.city` optimizes lookup performance.

## How it works (follow ONE request/click end to end)
- When a manager defines a new room type for a hotel:
  1. The manager submits room details (title, capacity, price in Toman, quantity, selected amenities).
  2. The backend creates a `RoomType` instance linked to the manager's `Hotel`.
  3. PostgreSQL checks that `(hotel_id, title)` is unique in the table, `capacity >= 1`, and `quantity >= 1`.
  4. The M2M intermediate table links the selected `Amenity` IDs to the newly created room type.
  5. The created room type is immediately queryable via `hotel.room_types.all()`.

## Gotchas / things that surprised us
- In Django models with `CheckConstraint` on nullable fields like `star_rating`, it's critical to write `Q(star_rating__gte=1, star_rating__lte=5) | Q(star_rating__isnull=True)` in the check condition, so that leaving `star_rating=None` does not violate the constraint in PostgreSQL.

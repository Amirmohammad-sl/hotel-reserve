## Why / design decisions (and alternatives rejected)
- **Separation of Concerns: Application vs. Security Loggers**: Used `logging.getLogger(__name__)` for normal application workflow logging (CRUD success/validation errors), but explicitly routed authentication and authorization events to `apps.security`. As configured in `backend/config/settings.py` (P3-08), `apps.security` streams directly into `logs/security.log`, providing auditability for suspicious activities (e.g. repeated failed logins or role probing).
- **Log Levels by Semantic Severity**:
  - `DEBUG`: Routine read operations and diagnostic metadata (e.g., search results count, list sizes, session lookups).
  - `INFO`: Normal state mutations (e.g., successful registration, login, logout, entity creation, entity update/deletion, and benign public 404s).
  - `WARNING`: Form validation errors, malformed payloads, login rejections, and access denied events (e.g., accessing someone else's hotel).
  - `ERROR`: Unhandled 500 exceptions with `exc_info=True` for automated traceback analysis in `logs/error.log`.
- **Zero Sensitive Data Principle**: Under Hard Rule 9, passwords, raw secrets, and session hashes are strictly omitted from log statements. For failed logins, only the submitted identifier (`username_or_email`) and client IP are logged, preventing plain-text password leakage into log files.

## How it works (follow ONE request/click end to end)
1. **Manager registers a new hotel via `POST /api/manager/hotels/`:**
   - Request enters `RequestLogMiddleware`, which records start timestamp.
   - `role_required("manager")` decorator checks user authentication and verifies `request.user.role == "manager"`.
   - `manager_hotels_list_create_view` validates input payload against `HotelForm`.
   - If form validation succeeds, the hotel is saved with `owner = request.user`.
   - View emits: `logger.info("Manager created hotel: hotel_id=%s name='%s' city='%s' user_id=%s", hotel.id, hotel.name, hotel.city, request.user.id)`.
   - The formatted log entry is written to `console` and appended to `backend/logs/app.log`.
   - The response (201 Created) bubbles back through middleware, where latency and status code are logged.

## Gotchas / things that surprised us
- In `backend/apps/accounts/views.py`, `LoginForm` uses the field name `username_or_email` rather than `username`. When logging failed authentication attempts, checking `data.get("username_or_email") or data.get("username")` ensures the submitted identifier is captured accurately without logging the submitted password.
- Using `assertLogs` in Django tests requires specifying the exact logger name (or parent hierarchy, e.g. `apps.security`) and an appropriate level. When inspecting output from child loggers, setting the root or module level properly guarantees log capture without test pollution.

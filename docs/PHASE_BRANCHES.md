# مدل برنچ فازی (Phase Branches) — نسخه ۲ کیت

هدف: پروژه را **زودتر تمام کنیم** ولی هر فاز را **سر موعدش تحویل بدهیم**.
فازهای ۲، ۳ و ۴ روی برنچ‌های بلندمدت `phase/2`، `phase/3`، `phase/4` ساخته می‌شوند و فقط روز تحویل به `main` می‌روند.

## ۱. نقشه برنچ‌ها
```
main        ●──────────────●(merge فاز ۲، تگ phase-2)───────●(merge فاز ۳، تگ phase-3)────●(تگ final)
             \            /                                 /                              /
phase/2       ●──●──●──●─●                                 /                              /
               \          \                               /                              /
phase/3         \          ●──●──●──●──●──●──────────────●                               /
                 \                      \                                               /
phase/4           \                      ●──●──●──●──●──●──────────────────────────────●
task branches:  feat/P2-03-… → PR به phase/2 ؛ feat/P3-01-… → PR به phase/3 ؛ feat/P4-01-… → PR به phase/4
```
- **stacked (پلکانی):** `phase/3` همیشه همه چیزِ `phase/2` را دارد و `phase/4` همه چیزِ `phase/3` را. جریان تغییرات فقط **رو به پایین** است: `main → phase/2 → phase/3 → phase/4`.
- `main` فقط حالت تحویل‌شده است. هیچ‌کس مستقیم روی `main` یا `phase/*` کامیت نمی‌زند.

## ۲. قواعد
| موضوع | قاعده |
|---|---|
| برنچ تسک | از برنچ فازِ همان تسک ساخته می‌شود: `P2-xx→phase/2`، `P3-xx→phase/3`، `P4-xx→phase/4`. (`python scripts/board.py --base P3-01`) |
| PR تسک | به برنچ فاز، **Squash** |
| PR انتقال (propagate) | از فاز بالادست به پایین‌دست، **Merge commit** (هرگز squash) |
| PR تحویل | `phase/N → main`، **Merge commit**، برنچ حذف نشود |
| باگ فاز قبلی | `/phase-fix` روی برنچ همان فاز، بعد `/propagate` |
| تحویل | فاز N فقط بعد از تحویل فاز N−1 |
| هر روز | `/sync`؛ اگر چیزی در فاز بالاتر merge شد، همان روز `/propagate` |

چرا Squash برای تسک و Merge commit برای بقیه؟ اگر PR انتقال یا تحویل squash شود، تاریخچه مشترک از بین می‌رود و برنچ‌های پلکانی با هم conflict عجیب می‌گیرند.

## ۳. چرخه کار روزانه (دو اپراتور)
1. `/sync` → وضعیت پشته (آیا فازی عقب است؟) + PR های منتظر review.
2. `/next` → حالت‌ها: ▶ READY · ↧ UPSTREAM (باید `/propagate` شود) · … WIP · ✖ BLOCKED.
3. چرخه تسک مثل قبل (`/task-start` → `/commit` → `/verify` → `/task-pr` → `/review-pr` → `/merge-pr`) ولی **base = برنچ فاز**.
4. بعد از merge یک PR در `phase/N`: بررسی `/propagate` برای پایین‌دست‌ها.
5. پایان روز `/end-session`.

### چطور سریع‌تر تمام می‌شود؟
- تسک فاز ۳ و ۴ که به تسک‌های فاز ۲ وابسته نیستند (مثلاً Manager ها، logging infra، تست‌ها) را همان لحظه که READY هستند شروع کنید (به‌جای منتظر ماندن برای «دروازه فاز ۲»).
- وابستگی‌ها حالا «واقعی» هستند، نه «بعد از دروازه». `board.py` می‌گوید چه چیزی را الان می‌توانید شروع کنید.
- روز تحویل فقط یک PR و چند دستور است؛ همه آماده‌سازی‌ها (`/phase-close`) قبلاً انجام شده.

## ۴. آماده‌سازی و تحویل هر فاز
**آماده‌سازی** (هر زمان بعد از اتمام تسک‌های `must` فاز): تسک دروازه (`P2-12` / `P3-11` / `P4-18`) را با `/task-start` شروع کنید و داخلش `/phase-close N` را بزنید: تست clean-clone، بکاپ دیتابیس از یک DB موقت، اسکریپت ارائه `docs/demo/phase-N.md`، چک‌لیست خروج. بعد `/task-pr` و merge به `phase/N`.
**تحویل** (روز تحویل): `/phase-deliver N` → PR `phase/N → main` (merge commit) → تگ `phase-N` → تمرین ارائه با `/viva-drill phase N`.
**ارائه:** از تگ `phase-N` (یا `git worktree add ../hotel-demo-N origin/phase/N`) و dump فاز استفاده کنید، نه از دیتابیس روزمره‌تان که ممکن است جلوتر باشد.

## ۵. ریسک‌ها و راه جلوگیری
| ریسک | راه جلوگیری |
|---|---|
| عقب‌ماندن فازهای پایین‌دست و conflict بزرگ | `/propagate` همان روز؛ `/sync` عقب‌ماندگی را نشان می‌دهد |
| Migration در دو فاز برای یک اپ | تغییر اسکیما را در **اولین** فاز ممکن بدهید؛ در conflict: `makemigrations --merge` |
| `main` جلوتر از `phase/*` بشود | روی main فقط merge تحویل؛ اگر چیزی رفت، `/propagate` از main |
| باگ فاز ۲ بعد از شروع فاز ۳ | `/phase-fix 2 …` و بعد `/propagate` |
| Dump اشتباه | فقط از DB موقتِ ساخته‌شده از همان برنچ (`/db-backup`) |
| فراموشی ترتیب تحویل | `/phase-deliver` شرط‌ها را چک می‌کند |

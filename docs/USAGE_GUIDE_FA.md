# راهنمای استفاده از Agent Kit (فارسی)

## ۱. کیت چیست؟
کیت = قوانین ثابت برای ایجنت + تسک‌های از پیش‌چیده‌شده + دستورهای اسلش برای چرخه کار + اسناد قرارداد (مدل داده و API).
ایجنت (Flash) سریع است ولی با زمینه طولانی ضعیف می‌شود؛ پس همه «حافظه» در گیت و فایل‌هاست، نه در چت.

| پوشه/فایل | کار |
|---|---|
| `AGENTS.md`, `GEMINI.md`, `.agent/rules/*` | قوانین همیشه‌فعال (استک، گیت، Django، React، پروتکل دو نفره) |
| `.agent/workflows/*` | ۲۰ دستور اسلش (`/sync`, `/task-start` …) |
| `docs/tasks/phase-0..4.md` | ۵۷ تسک با Owner، وابستگی، DoD |
| `scripts/board.py` | برد تسک‌ها (`--me`, `--next`) |
| `docs/DATA_MODEL.md`, `API_CONTRACT.md`, `DECISIONS.md` | قراردادهای مشترک |
| `docs/journal/` | یادداشت هر تسک + سوال‌های احتمالی استاد |
| `docs/VIVA_PREP.md` | بانک سوال تحویل |
| `.github/` | CI و قالب PR |
| `scripts/backup_db.sh` | بکاپ PostgreSQL (الزام درس) |

## ۲. راه‌اندازی اولیه (یک‌بار)
1. **اپراتور A:** پوشه کیت را در یک پوشه خالی کپی کند، در Antigravity باز کند، یک بار روی ایجنت بگوید: «`/bootstrap`». سپس تسک **P0-01** (ساخت ریپو GitHub، دعوت B، محافظت از main).
   - اگر نسخه Antigravity شما پوشه‌های دیگری برای rules/workflows می‌خواند (مثلاً `.agents`)، همین پوشه‌ها را با همان نام جابه‌جا کنید؛ محتوا یکی است. در پنل Customizations باید قوانین و workflow ها را ببینید.
   - پیشنهاد: Terminal policy روی «درخواست تایید» باشد (به‌خصوص برای git/rm/db).
2. **اپراتور B:** ریپو را clone کند، باز کند، `/bootstrap`، سپس تسک **P0-02** (اولین PR کامل چرخه).
3. هر دو: `git config user.name/email` را درست بزنید و ایمیل را در `docs/TEAM.md` بنویسید (ایجنت از روی همین شما را تشخیص می‌دهد).
4. B ایمیل به استاد (P0-06) را همان روز اول بفرستد.

## ۳. قواعد طلایی
- **هر تسک = یک چت جدید** + یک برنچ + یک PR. وسط کار چت طولانی شد؟ چت جدید باز کن و دوباره `/task-start <ID>` (ادامه روی همان برنچ).
- قبل از کد، **پلن را بخوان و تایید کن**؛ اگر چیزی را نفهمیدی بپرس: «چرا؟».
- به ایجنت اجازه نده Contract را عوض کند → `/pair-contract`.
- چیزی را merge نکن که نتوانی توضیح بدهی؛ `/review-pr` عمداً از تو سوال می‌پرسد.
- Antigravity را روی Planning بگذار برای تسک‌های M/L.

## ۴. چرخه هر تسک — به تفکیک اپراتور
هر تسک یک **نویسنده (Author = Owner)** و یک **بازبین (Reviewer = نفر دیگر)** دارد. بنابراین چرخه برای هر اپراتور دو نقش دارد.

### الف) وقتی تو Author هستی (تسک خودت)
| # | دستور | چه می‌شود | خروجی |
|---|---|---|---|
| 1 | `/sync` | pull، ادغام main در برنچ، گزارش فارسی کامیت‌های همتیمی، چک نصب/migrate | آگاهی از کارهای او |
| 2 | `/next` | تسک‌های آماده‌ی تو | انتخاب تسک |
| 3 | `/task-start P1-04` | بررسی وابستگی، ساخت برنچ، خواندن زمینه، **پلن** | پلن؛ تو تایید می‌کنی |
| 4 | (کدنویسی ایجنت) | گام‌به‌گام | تغییرات کوچک |
| 5 | `/commit` | چک سریع، کامیت استاندارد با Task-ID، push | کامیت قابل توضیح |
| 6 | (تکرار 4–5) | | چند کامیت |
| 7 | `/verify` | check، migrations، test، lint، build، DoD با شواهد | جدول PASS/FAIL |
| 8 | `/task-pr` | journal + سوال‌های ارائه، Status=DONE، docs، push، باز کردن PR | PR + پیام برای همتیمی |
| 9 | منتظر review → `/next` | کار بعدی یا Review PR همتیمی | |
| 10 | اگر درخواست تغییر آمد | اصلاح + `/commit` + `/verify` + push | |
| 11 | `/end-session` (پایان روز) | WIP کامیت، push، یادداشت تحویل | |

### ب) وقتی تو Reviewer هستی (تسک همتیمی)
| # | دستور | چه می‌شود |
|---|---|---|
| 1 | `/sync` | PR های منتظر نمایش داده می‌شود |
| 2 | `/review-pr 12` | checkout، **آموزش فارسی تغییر** (برای اینکه به استاد جواب بدهی)، اجرای چک‌ها، چک‌لیست review |
| 3 | (پاسخ به ۲ سوال) | «دروازه درک»؛ اگر غلط بود ایجنت توضیح می‌دهد |
| 4 | تصمیم Approve/Request changes | ایجنت review را روی GitHub ثبت می‌کند |
| 5 | `/merge-pr 12` | squash merge، به‌روزرسانی main، گزارش اینکه چه تسک‌هایی آزاد شد |

### ج) دستورهای کمکی
`/status` وضعیت · `/explain <فایل|کامیت|PR>` توضیح فارسی · `/viva-drill` ایجنت نقش استاد · `/decision` تصمیم معماری · `/pair-contract` تغییر قرارداد · `/blocker` گیر کردن · `/conflict` تداخل گیت · `/db-backup` بکاپ · `/phase-close N` تحویل فاز · `/report-section` تولید بخش گزارش.

## ۵. شروع عملی: روز اول هر نفر
**اپراتور A:** `/bootstrap` → `/task-start P0-01` (ریپو، محافظت main، دعوت B) → بعد `/task-start P0-03` (اسکلت Django+Postgres) → وقتی PR اول B آمد `/review-pr`.
**اپراتور B:** منتظر P0-01؛ سپس `/bootstrap` → `/task-start P0-02` → `/task-start P0-04` (اسکلت React/Tailwind) و `P0-06` (ایمیل به استاد) → سپس `/task-start P1-02` (دیاگرام‌ها) تا A مدل‌ها را برساند.
بعد از هر merge: `/sync` و `/next`.

## ۶. تا ارائه به استاد
- هفته‌ای یک‌بار: `/status` + هرکس `/viva-drill` روی کار دیگری.
- قبل از هر تحویل: `/phase-close N` با هم.
- فاز ۱: ایمیل لینک ریپو **یک روز قبل** از موعد (در تقویم یادآور بگذارید).
- مهم: کامیت‌ها باید با نام هر نفرِ واقعی ثبت شوند (git identity درست) و هر دو نفر تسک و PR داشته باشند؛ `/status` توازن را نشان می‌دهد.

## ۷. عیب‌یابی
| مشکل | راه‌حل |
|---|---|
| ایجنت از کیت پیروی نمی‌کند | چت جدید، اول بگو «AGENTS.md را بخوان» و بعد `/task-start` |
| `board.py --me` اپراتور را نمی‌شناسد | ایمیل `git config user.email` با `docs/TEAM.md` یکی نیست |
| وابستگی بلاک شده | `python scripts/board.py` ببین منتظر چه تسکی است؛ `/review-pr` همان را سریع‌تر کن |
| conflict | `/conflict`؛ هرگز `reset --hard` نزن |
| migration دو سر شد | `python manage.py makemigrations --merge` |
| ایجنت قرارداد را خراب می‌کند | `/pair-contract` و تغییر را در PR جدا |
